2026-08-06 使用者問「好像每次讀取器都有問題,你要不要檢查一下 SKILL」。查下去確認
不是每次運氣不好,是 `gen-vendor-parser` 產線本身有系統性缺陷。

## 三次事故都指向同一個根因

| 事故 | 表面問題 | 根因 |
|---|---|---|
| 金大 v1(2026-08-05) | 單位被讀成 `RC` | skill 曾建議用樣式判定 `/^[A-Z]+\d*$/` 猜單位 |
| 金大 v2(2026-08-06) | 累計數量被讀成本日完成數量 | skill 教「以第一個單位 token 切名稱\|數字欄」= 靠順序推欄 |
| 富森(2026-08-06) | 長名稱跨行重組錯位,六成名稱是錯的 | 同上,且三道關卡全看不到 |

**skill 教的是會錯位的方法,所以錯法被反覆複製。** 且 skill 只介紹
`extractPages`(純文字),完全沒提 `extractItems`(座標版)——而後者早在 SP3 就已是
「多欄表格 PDF 一律走」的定案,**規則沒同步進產線**。正典範例的描述也停在舊版。

## 驗收的兩個結構性盲區(這才是最值得記的)

1. **完整性關卡只看欄位是否為 null**,而**名稱被切錯不會讓任何欄位變 null**。
2. **跨層驗證預設拿日誌自己的第一次出現值當契約基準**——讀取器若每天都用同樣方式
   讀錯,**自我比對永遠一致**。系統性讀錯正是讀取器最典型的壞法,而關卡對它完全免疫。

富森就是靠這兩個盲區通過交付的,直到接上真實契約表跑完整 pipeline 才現形。
**通用教訓:任何「用自己的輸出當基準」的驗證,對系統性錯誤都是瞎的。**

## 已補(2026-08-06,分支 `fix/e1-name-fallback`)

- SKILL:PDF 多欄表格改為座標歸位(依 y 分行 → 表頭取欄界 → `w/s.length` 推字元 x →
  token 中心歸欄 → **中心落在欄與欄之間就不指派**);正典範例標明 v1.0.0 純文字版不要當樣板。
- `check-parser.js` 關卡 b 加**名稱形狀健檢**(標點開頭/括號不對稱/名稱過短),
  不需外部基準,八家實測**零誤報**——只有富森 10 項、陳宏鈞 1 項命中,都是真的被切錯。
  已納入通過判定。
- `check-parser.js` 加 `--contract <工程id>`,改用真實契約表當外部基準。
  實測富森 E3 從 1679(自我)→ 3187(外部)。**手上有契約表就一定要跑這個模式。**

## 富森的名稱重組已修(2026-08-06)

改成「每個名稱片段歸給 y 最近的項次列」,並以表頭列為資料區上界(頁首的校名/天氣/
工期也落在名稱欄的 x 範圍內,不設界線會被吸進第一個項次)。
名稱逐字對上 38% → 49%,名稱形狀健檢 10 → 5 項。

**一條試過行不通的路,別再試**:想用「名稱 item 與項次 item 的 y 差」判斷名稱是否在
項次自己那列(自足),好讓長名稱的最外側片段不被自足鄰居搶走。**這個版面把數值垂直
置中於名稱區塊**,所以多行名稱的中間那行必然與數值幾乎同高(項次4 差 0.9、項次2 差 0.4),
兩者無法用閾值區分,硬分反而把常見情況判錯。

剩餘的名稱對不上經抽樣查證**全是廠商用詞差異,不是讀取器錯位**:全形/半形標點、
簡寫(`10*10cm` vs `10cm*10cm`)、用詞(抹縫 vs 勾縫)。

**標點差異已在驗證層解掉**(2026-08-06):`daily-log-validate` 的 `squash` 改為
先 NFKC 再去空白,把全形英數與標點折成半形。**逐字對上率 49% → 68%**,富森 E3 2861 → 2370。
刻意不統一「、」與「,」——語意不同(頓號列舉 vs 逗號分句),硬統一是換一種誤判,
實測也無額外效益。剩下的簡寫與用詞差異屬廠商填寫習慣,不該由程式猜。
