2026-07-25 與使用者 brainstorming 定調:「施工日誌轉監造報表」不是從零產表,而是**把值注入使用者提供的 .xlsm 範本、讓範本自身公式去算**。

**範本是自算活頁簿**,7 分頁,只有 3 個區塊要填原始值,其餘全公式帶出:
1. `工程基本資料`(B1:B8,B10 共 9 值)→ 封面/封面(2)/監造報表 全靠 `INDEX/MATCH` 自動帶;B9 完工期限=`B8+B7-1` 公式。
2. `契約詳細價目表`(A:E 項次/項目/單位/數量/單價)→ F 複價=公式;`每日施工紀錄` A~F 列 `=INDEX(契約詳細價目表…)` 自動拉。
3. `每日施工紀錄` 日期欄塊填「本日完成數量」→ 累計數量/金額/完成% 全自動。**日期欄是公式錨定的**:`J1 = 工程基本資料!B8`(開工日)、`K1=J1+1`…到 `ACH`(約 753 天),故「某天寫哪一欄」= `J + (填報日期 − 開工日期)`,deterministic。

**真實工作流程**:決標公告 → 審核開工報告表 → 填工程基本資料 → 發包經費總表填契約詳細價目表 → 施工日誌經驗證後補每日施工紀錄 → 依廠商公文產我方公文(我方日期 ≥ 廠商日期)。

**子專案**:SP0 範本填寫引擎(基座)、SP-P 廠商讀取器 onboarding、SP1 工程基本資料、SP2 契約詳細價目表、SP3 每日施工紀錄+驗證、SP4 公文。

## SP1 學到的硬事實(寫 SP2/SP3 前必讀)

見 [[sp1-award-notice-findings]] 的完整清單。最關鍵三條:

1. **開工報告表 24/25 是掃描件**(可抽文字=0),正式環境無 AI/OCR ⇒ 走不了固化讀取器。決標公告則 28/28 有文字。
2. **契約工期推不出來**——決標公告的「履約起迄日期」是預估值,27 組驗證只有 14 組與實際契約工期相符;28 份決標公告全部欄位皆無記載工期。契約工期與開工日期一律人工輸入。
3. **`excel-com-driver.ps1` 曾有致命 bug**(SP1 Task 12 修掉,commit `28d2f5a`):PS 5.1 依「該 call site 第一次遇到的值型別」快取 COM property setter 繫結,混型別 setCell 批次整批失敗。SP0 沒測出是因為它的值全是數字。**SP2/SP3 若送混型別批次,靠的就是這個修正**。

**跨切面決策**:硬錯阻擋產出+列全部錯誤(不給強制產出);金額一律 `roundHalfUp`;專案報表 `.xlsm` 是 SP1/SP2/SP3 共用的**常駐檔**(`data/reports/project_<id>/監造報表.xlsm`),已存在絕不覆蓋——覆蓋等於洗掉其他 SP 的成果。

**現有 `report.js`**(從零手刻附表五)已被範本填寫路線取代;UI 上兩條路線暫時並存(舊的產 `data/output/proj_<id>/*.xlsx`),SP2–SP4 落地後應退役。
