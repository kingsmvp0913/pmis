## 新成:真正的坑是「兩套名稱」

版面本身單純(單一 `施工日報` 分頁、一天 73 列、27 天)。坑在:

**B 欄與 C~G 欄是兩個不同的合併區,裝著兩套不同的名稱**,從項次 12 起就對不上:
```
項次12  B=安裝360度吊扇            C~G=小便斗拆除與更新
肆      B=包商管理及利潤費(約壹*7%)  C~G=安全衛生及管理費(約0.6%)
```
C~G 是上一個案子的殘留。**以發包經費總表逐項核對,B 欄才對**。
取錯欄不會有任何欄位變 null——這正是 [[parser-pipeline-gaps]] 說的那種。

同一個病還有一處:**契約數量取欄 8**,費用列的欄 9~10 是殘留的 10。
**主體項目三欄同值,所以只看主體永遠看不出來**,費用列才會現形。

進度是 skill 記的國謙那型:**同一列預定是百分數(1)、實際是分數(0.0128)**。
依整份最大值分別判斷兩欄再統一;**不可逐日判斷**(開工前幾天兩欄都很小)。

驗收:27 天 × 17 項、單位/數量/單價零 null、名稱健檢零異常、SP3 硬錯 0、
外部基準名稱/單位/數量 **17/17 全對**。

## ⚠️ 銘佑:掃描件**不是不能做**,卡的是「沒有項次欄 + 名稱錯字」

`龍井國小七月份施工日誌.pdf` 無文字層(4 頁、`extractItems` 回 0 個 item)。

⛔ **我第一時間判成「掃描件做不了」是錯的**,因為 SKILL.md 還寫著舊規則
——`daily-log-scan.js` 的 `scanDays` 在 2026-08-10 就開放了。已改寫 SKILL(`8dfb063`)。

實跑 OCR(2200,43 秒)的結果:
- **`scanCoverage` 完美**:4 頁 = 封面 + 3 天(7/29~7/31),日期/星期/天氣全讀到,
  封面也讀出「承包廠商:銘佑營造有限公司」。
- **明細的數字讀得不錯**(1.00 / 0.50 / 592.00 / 23.00)。
- ❌ **真正的障礙有兩個**:
  1. 這份是**雙欄版面**(左半 x45~280、右半 x295~532,各一組
     「施工項目/單位/派工數量/本日完成數量/累計完成數量」)。
  2. **沒有項次欄**,只能拿名稱當 key——而 OCR 的名稱錯字率高得驚人:
     `乙種施工团`(圍)、`速工带料`(連工帶料)、`给排水`、`折除`、`搞播`、`范圍`、
     `练材`、`黄任`,幾乎每個項目 1~3 個錯字。

**所以讀取器寫得出來,但每一列都對不上契約表**,承辦人的「逐格確認」會變成
「逐格重打」。要先解決**名稱模糊比對**(比對層的題目,與宏恩那件同一個,
見 [[ocr-merged-box-gap]])。**這一項還沒問使用者要不要做。**

## ⛔ 我一度把「隱藏欄」當成簽約金額——使用者一句話就戳破

我原本登記成「總額一致但各項單價錯的第一個實際案例」。使用者問
**「新成的施工日誌哪裡有價格?」**,一查就知道站不住:

**那一欄在 Excel 裡是隱藏的。** 表格右邊 **R~V 五欄全部隱藏**,裝著
`S 累計完成數量 / T 單價 / U 累計完成金額(=S*T)`——**承辦人在畫面上根本看不到**,
那也不是他向機關申報的內容。

**裁決(使用者 2026-08-15):不讀隱藏欄的單價,留空**,契約單價一律以發包經費總表為準。
照讀的話這一案每天都被 E6 擋下(14 項 × 27 天),而原因只是廠商自己都看不到的一欄。

📌 **通則已寫進 SKILL.md 的 Excel 那節:隱藏欄是廠商的工作區,不要讀。**
判斷 `ws['!cols'][i].hidden`。⚠️ **逐格比對永遠看不出來**——值都在、也自洽,只是不該用。

⚠️ 數字本身仍然成立(17 項裡 14 項不同、逐項複價合計兩邊都是 1,193,638、差額 0),
**只是不足以推論簽約金額**。已把「只比總額不夠」那條原則底下的例證撤掉——
那條原則仍然成立,但**目前還沒有實際案例**;留一個錯的例子比沒有例子更貴。

## 教訓:先問「這個欄位承辦人看得到嗎」

這一輪連續兩次被同一種東西騙:C~G 欄的**別案殘留名稱**、R~V 的**隱藏計算區**。
兩者都是「值都在、也自洽,但不是這份文件要表達的內容」。

## ✅ 2026-08-15 銘佑做掉了(`fdae060`)——**而且不必做名稱模糊比對**

⛔ **上面那段「要做得先解決名稱模糊比對」是錯的判斷。先量再做,結論完全不同。**

### 先查清楚是哪一案(差點做錯案)

同一所學校有**兩個龍井案**:
- **龍井球場**(新建綜合球場)→ 得標廠商 **經緯營造股份有限公司**,已有讀取器 `jingwei`,
  而且 `全案範例\龍井球場\` 裡有 **14 份 .xls 施工日報表**(有文字層)。
- **龍井廁所**(老舊廁所整修)→ 得標廠商 **銘佑營造有限公司**,只有那份掃描件。

📌 **看到「同一所學校」先確認是哪一個標案**——決標公告的得標廠商才是判準。

### 為什麼不需要模糊比對

那份**每天都印完整的 35 項,順序與發包後經費總表一字不差**,所以項次用「出現序」即可。
名稱的 OCR 錯字只讓 E3 出軟警告——那正是要讓承辦人看到的。

**驗收(35 項 × 3 天,對發包後經費總表):項次 105/105、契約數量 105/105、
單位 104/105。接上真實契約表跑 SP3:硬錯只有 1 個(那個 OCR 沒讀到的單位),E1 = 0。**

### ⚠️ 列錨必須用「派工數量」,不可以用單位

7/30 那頁的「片」(項次19 的單位)**OCR 沒讀到**。以單位當列錨會少一列,
而**後面 16 項全部位移一格**——每一格都還是合法數字,SP3 一條都不會叫。
三天的派工數量序都與契約表完全一致,那才是穩定的錨。

### 四個版面坑(雙欄掃描件通用)

1. **橫跨兩欄的 item 要切開**(「0.50貼深色石材面…」= 左欄累計 + 右欄名稱)。
   切點**只認「開頭是一個完整數字」**;用欄界換算字元位置會誤傷單純比較寬的格子
   ——工程名稱那一格被切成「…國民中小學老舊廁」+「所整修工程」。
   正規表示式要加 `(?![\d.])`,否則「1.00」被回溯成「1.0」+「0」。
2. **名稱歸給「它下方最近的錨」**:數值一定印在名稱區塊的最後一行,續行在上方。
3. **單位在錨的下方約 5pt**,而且同一個合併格可能被 OCR 讀兩次(接起來變「式式」)。
   取「錨下方一個列距內最靠近」的那一格;讀不到就 null,不猜。
4. **OCR 逐字插空格**(「營 業 稅」)。比對費用項目前要去掉,否則項次變成 31、32。
   ⚠️ **只清「中文與中文之間」**——數字之間的空格清掉會把 `115 7 29` 黏成一個數字。
