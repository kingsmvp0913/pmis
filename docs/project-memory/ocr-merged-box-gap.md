## 病徵:錨點要求「整格剛好等於標籤」,而 OCR 會併框

OCR 的偵測框不保證跟版面的儲存格一致,實測三種壞法:

| 期望 | OCR 實際讀出 | 壞法 |
|---|---|---|
| `表單編號:` | `表單編號：33` | 標籤+值併成一格 |
| `本日天氣:` | `本日天氣：上午： 雨` | 同上,跨了兩個欄位 |
| `表報編號…` | `編號：90` | 標籤被吃掉一半 |
| `本日天氣…` | `天氣：` | 同上 |
| `單位`(直排兩字) | (完全沒有框) | 整個沒偵測到 |

**症狀一律是整份 throw 或整欄 null,不是讀錯**——所以在數字上看不出來,
只會看到「這份不能用」。

## ✅ 施工日誌那半已修(`ef3f054`、`0f00fb4`)

三支讀取器,三種修法:

1. **宜謙**:表頭「單位」沒被偵測到 → **從欄內的值回推欄界**(單位是封閉白名單、
   幾乎每列都有)。校準:文字層表頭 x=392.9、單位值最小 x=393.2,故取
   「叢集最小 x − 0.5」。實測饒平 4/25-4/30 **對 6、錯 0、漏 0**。
2. **嘉原**:挑頁與明細表頭都要求整格相等 → **兩段式**。實測民生球場 4 月
   31 頁全解析、30 天有日期,**對 18、錯 0、漏 0**。
3. **宏恩**:同上 + 放寬挑頁會把第二聯選進來 → 同一天只留明細最多的那頁。
   從整份 throw 變成讀得出日期/天氣/38 列,但**明細品質仍差**(項次與名稱併成
   一格:「22必要之側封板與窗簾盒批土刷漆)」),**不宣稱宏恩可用**。

⚠️⚠️ **兩段式一定要做在「整份文件」層級,不可以逐頁判斷。** 踩過:讓每頁各自
「嚴格找不到就放寬」,文字層的嘉原立刻 30 天變 31 天——多出來那筆沒有日期卻有
明細數量,是一頁本來就不是日誌的頁被放寬後憑空生出來的。正確做法是挑頁時記下
「這份是不是被迫放寬」,再把那個旗標傳進 parsePage。

## ⚠️ 兩個「以為是併框、其實不是」的更正(2026-08-11 收工前查的)

**① `大勇廁所` 不是單純的併框,它是臺中市格式。** 快取實測第 1 頁只有 78 個 item,
`工程名稱` 的值(`114學年度南棟教室西侧厕所整修工程`)與標籤各自分開、位置也不同,
還有一堆空字串 item 與雜字(`无`、`司`)。臺中市格式的坑另有專篇
[[kickoff-taichung-format-findings]](標籤逐字水平散開)。
**它吃掉 6 個漏是真的,但修法要走臺中市那條線,不是併框那條。**先估工再開工。

**② 宏恩的明細不是「項次與名稱併框」。** 那個格式**根本沒有項次欄**——
讀取器是拿**名稱當項次**(檔頭寫著「此格式沒有項次欄,逐日只列當天施作的項目,
出現序跨天會指到不同項目,故項次用項目名稱」)。所以看到的
`22必要之側封板與窗簾盒批土刷漆)` 是**名稱本身帶了 OCR 雜訊**,不是兩欄併在一起。
要讓宏恩的掃描件可用,得做**名稱的模糊比對**(比對層,不是讀取器),
那是另一個題目,別當成併框順手修掉。
