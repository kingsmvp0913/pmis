使用者問「我不是有監造報表範例嗎?產出監造報表和範例完全不一樣啊」——這是
[[user-feedback-17-items]] 第 3/4 項一直找不到的真正原因:**打開來滿滿 `#N/A`**,
不是數值錯。2026-08-11 已修完,饒平案公式錯誤 **0 個**(與人工範例同)。

⚠️ **教訓**:比對「值對不對」與「打開來像不像」是兩件事。
`build-and-compare` 全綠不代表報表可用——它從來只比值。
(饒平案:契約詳細價目表 30/30 一致、每日施工紀錄 129 格 0 矛盾,同時卻有 3047 個公式錯。)

⚠️ **修範本的一次性腳本都在 `data/parser-tools/`,而 `data/` 是 gitignore 的**
(`.gitignore:5`)——腳本進不了 git,**只有被改過的 .xlsm 進得去**。重 clone 就沒有
那些腳本,要再改範本得照本篇描述重寫。既有的 `fix-template-na.js` 也是同樣情形。

## 四道修法(饒平案 3047 → 0)

| # | 腳本 | 剩餘錯誤 |
|---|---|---|
| ① | `fix-template-na.js` | 3047 → 35 |
| ② | 手改 `監造報表!N8` | 35 → 4 |
| ③ | `fix-template-progress-labels.js` | 4 → **13** ⚠️ |
| ④ | `fix-template-blank-row-errors.js` | 13 → 0 |

③ 之後總數**上升**,不是做壞了——是 ① 把 `#N/A` 換成了 `#VALUE!`,而 ③ 讓被毒到的
合計列浮出來(見 ④)。監造報表分頁本身在 ③ 之後就 0 個錯了。

**①** `IF(契約詳細價目表!A32="",NA(),…)` → `""`。範本項目列鋪到第 37 列、真實案子
20~40 項 → 用不到的列每格 `#N/A`,乘上 595 個日期欄就是三千多個。人工報表沒這問題
是因為承辦人**把用不到的列整個清空**。已確認全檔 0 處 ISNA/IFERROR/ISERROR/IFNA。

**②** `監造報表!N8` 原本寫死 46203(2026-06-30),是某個舊案留在範本的殘留值。
那是「這份報表的填報日期」,每份新報表都拿到同一天,而該案日期欄不含那天 →
`MATCH($H$3, 每日施工紀錄!$1:$1, 0)` 找不到。改成 `=工程基本資料!B8`(開工日)。

## ③ 進度統計列:**範本沒有缺那五列,只缺標籤**

先前記為「公版範本完全沒有進度統計列,可能根本不是他們在用的那份」——**實測不是,
不要再往「換範本」的方向走**。那五列的公式完整存在於範本第 285~289 列,與人工範例的
279~283 逐列同形(差 6 列是因為範本項目列預留到 37、該案只有 31):

```
範本 J285 = J$284/$F$284   人工 J279 = J$278/$F$278   每日實際進度(%)
範本 J286 = J285                                      實際進度
範本 J287 = ROUND($H$284/$F$284,5)                    總實際進度(%)
範本 J288 = J290           人工 J282 = J284           每日預定進度(%)
範本 J289 = J288                                      預定進度
```

缺的只有 **A 欄的標籤文字**(和合計列 `B284="(合計)"`)。`監造報表` 只有三格引用這裡,
全部靠字串比對——`MATCH("實際進度", 每日施工紀錄!A:A, 0)`(I5/F7)與 `"預定進度"`(B7)。
字串不在 → `#N/A`,而且整份報表就沒有進度統計。

## ④ 多餘列的算術公式:防護要判 0,不能只判空字串

饒平 30 項、範本鋪到 37 列 → 32~37 列是多餘的,那幾列的算術公式沒有防護:

```
每日施工紀錄 H32 = ROUND($G32*$E32,0)   E32 是 "" → #VALUE!
每日施工紀錄 I32 = ROUND($H32/$F32,5)   → #VALUE! / #DIV/0!
             H284 = ROUND(SUM(H2:H283),0)   ← 合計列被 H32 毒到
             J287 = ROUND($H$284/$F$284,5)  ← 總實際進度(%) 因此壞掉
```

修成 `IF(<來源格>="","",<原式>)`,沿用範本本來的慣用寫法而不是 IFERROR
(IFERROR 會把真正的 #REF!/#NAME? 一起吞掉)。三個踩到的點:

1. ⚠️ **除數只判 `=""` 接不住**。F 欄(契約複價)自己是 `ROUND(E*D,0)`,來源空白時
   算出來是**數字 0 不是空字串**,而 Excel 裡 `""=0` 是 **FALSE**。除數一律
   `OR(x="",x=0)`。第一版漏掉這點,6 個錯原封不動留著。
2. **原公式有兩種形狀**:H 欄第 2~32 列是 `ROUND($G*$E,0)`,第 33~37 列(費用項目)
   卻是 `G33*E33`——沒有 ROUND 也沒有 `$`。腳本要「讀出原式再包」,不能寫死形狀。
3. **契約詳細價目表 J34/L34/J36/L36 不是多餘列**。它們的 H/I/K 欄從頭到尾是空的、
   沒有欄位標題、也沒有任何程式會寫進去。對照人工範例,那一區是承辦人自己驗算費用
   項目百分比的草稿欄(`G27="（壹*0.6%）"`、`H28=26159`、`K28=0.006`)。範本留下的是
   把數字刪掉、公式忘了刪的殘留,和 `N8` 寫死 46203 同一類。一樣只包防護不刪除。

## 預定進度:改由系統依契約工期直線推算(使用者拍板)

第 289 列(預定進度)整列直接引用**第 290 列**——那是預定進度曲線的輸入列,人工報表
是承辦人依廠商的施工預定進度表逐格填的(饒平案 J~CH 共 77 格,0.12% 遞增到 51.1%)。
範本第 290 列是空的,系統也沒有這份資料 → 補完標籤後 `監造報表!B7` 會是 **0**,
看起來合法卻不是真的預定進度。

使用者選的是**直線推算**(與費用項目同一套規則,見 `daily-log-write.js` 檔頭):
`fix-template-planned-progress.js` 把 J290~WF290 共 595 格寫成

```
=IF(OR(工程基本資料!$B$7="",工程基本資料!$B$7=0,工程基本資料!$B$8=""),0,
    MIN(1,MAX(0,(J$1-工程基本資料!$B$8+1)/工程基本資料!$B$7)))
```

實測(工期 100 天):第 1 天 1%、第 50 天 50%、第 100 天(=B9 完工期限)100%、之後維持,
每日預定進度 1%/天、完工後 0。

- **寫成範本公式而不是 pipeline 寫值**:報表是常駐檔,工期或開工日之後被改時公式會
  自己跟著動,寫死值不會。
- **退場值取 0 不取 `""`**:第 288 列是 `K289-J289` 這種減法,空字串會變 #VALUE!,
  就是剛修掉的那類錯。
- 畫面標明放在 `daily-logs.js` 的 `renderPlanNote`(緊接既有的 `renderFeeNote`),
  報表版面不加註記——那是承辦人的決定。
- ⚠️ **工作天的案子這條線會偏快**:B7 存的是工期天數,工作天的案子那是工作天,
  而日期欄是連續日曆天。100 工作天的案子會在第 100 個日曆天就顯示 100%。
  範本裡沒有「日曆天/工作天」這個資訊(`duration_basis` 只在 DB,
  `project-basics.js` 的 `CELL_OF` 沒寫進分頁),要修得先把基準寫進分頁。**未做。**

## 使用者說的「不一樣」是**外觀**(2026-08-11 確認)

`#N/A` 只是其中一項。把產出檔與人工報表逐項比版面(分頁、!ref、合併格、欄寬、
列高、隱藏列、`!margins`)之後,共**五處**差異:

| # | 差異 | 狀態 |
|---|---|---|
| 1 | 項次:系統 `1`~`25`,人工 `壹.1`~`壹.25` | ✅ `e86b380` |
| 2 | 監造報表多印 5 列費用項目,正文被推下 5 列 | ✅ `56b4a54` |
| 3 | 監造報表 E/F 欄寬(範本 5.67/12.44,人工眾數 4.88 佔 46/49 案) | ✅ `b7b58c7` |
| 4 | 監造內容分頁整片空白 | 🟡 天氣 `fe33c5f`、表報編號 `b7b58c7`;其餘見下 |
| 5 | 每日施工紀錄與價目表的多餘空白列(人工整列刪掉) | ✅ `b7b58c7` |

**饒平實測(全部做完之後):四個分頁的 `!ref` 與人工報表完全一致**
(監造報表 Q136、價目表 Q278、每日施工紀錄 WF285、監造內容 R763),公式錯誤 0,
沒有 `#REF!`,欄寬差異全部 ≤0.11(= SheetJS wch 與 Excel ColumnWidth 的換算誤差,
實測差 0.22,**不是真的不同**——比欄寬時要先扣掉這個,否則會追一堆假差異)。

⚠️ **刪列順帶補了一個既有的洞:契約詳細價目表本來沒有擴列。** 項目值是 setRange
寫的沒有上限,但 **F 欄複價是公式 `ROUND(E*D,0)` 且只鋪到第 37 列**——49 案裡
2 案超過(三崙 38 項、簡易棒球場 49 項),第 38 列起複價是空的,再被每日施工紀錄
的 F 欄原封不動拉過去,完成百分比整列算不出來。**不補這個洞就不能刪列。**

**① 項次前綴**:49 個舊案人工報表 **42 份帶大類前綴**(饒平 `壹.1`、鎮西兩層
`壹.一.1`、古坑 `A.壹.1`)、6 份純數字。而**來源的經費總表全部**都是「壹」大類列 +
「1、2、3」,連那 6 份也是——**前綴是承辦人加的版面慣例,不是資料差異**。
⚠️ **不可以改項次本身**:7 家廠商日誌實測寫的都是純數字(只有東振寫 `A.壹.1`,
因為它的來源本來就有),而 SP3 是拿項次逐字當 key 對日誌
(`daily-log-validate.js` 的 `contractByNo`)。前綴只在 `contract-items.js` 寫 A 欄時組。

**② 刪列**:新增 `deleteRows` 指令(xlShiftUp)。三個非這樣做不可的點——
現有列數**一律讀實檔**(常駐檔可能已被刪過列或是承辦人上傳的,推錯會刪到報表
正文而且不會報錯,錨點是「二、監督」那一列,找不到就只擴不刪);擴列的來源列
改成「現存的最後一列」(範本原狀時算出來仍是 40,既有行為不變);**費用項目
沒有全排在尾端就不刪**(第 10+k 列一對一拉價目表第 2+k 列)。

**④ 監造內容**(2026-08-11 查完,49 案逐欄實測):

| 欄 | 內容 | 來源 |
|---|---|---|
| C/D | 天氣 上午/下午 | ✅ **日誌有**,讀取器 `天氣_上午`/`天氣_下午` 早就抽出來了,只是沒人寫。**28 案逐日不同的真天氣、21 案整份填「晴」** |
| A | 表報編號 | 純序號(A3=1、A44=42 = 列號−2),可推,未做 |
| L | 展延/不計天數 | ❌ 日誌沒有,**19 種值(0/1/2/4/9/11/13/70…)真的會非 0**,是監造判斷 |
| M | 停工天數 | ❌ 同上,4 種值(0/2/7/327) |
| N / O | 契約變更次數 / 變更後契約金額 | 49 案**全部都是 0**,但填 0 等於替承辦人斷言「沒有契約變更」 |
| E~I | 一、~五、的紀錄文字 | ❌ 監造人員自己寫的,抓不到 |

天氣的寫入:監造內容是**逐日一列**(`B3=工程基本資料!B8`、`B4=B3+1`…到第 763 列),
列 = `3 + (填報日 − 開工日)`,與每日施工紀錄的「逐日一欄」同一套換算換個軸。
越界只跳過那一天不 throw(天氣是附帶資訊,不該讓整份日誌卡住)。
`C2`/`D2` 的「上午」「下午」子標題公版範本漏了,**放在寫入指令裡而不是改範本**
——報表是常駐檔,這樣既有的專案報表也會一起補上。

## 重現方式

```
node data/parser-tools/build-and-compare.js "<全案範例>/11305饒平國小運動場" --keep
```
產出路徑印在最後一行。數公式錯誤:讀回來看 `cell.t === 'e'`,`v` 是錯誤碼
(**42 = #N/A**、7 = #DIV/0!、15 = #VALUE!、23 = #REF!)——SheetJS 不給錯誤字串,
第一次看到會誤以為那個 42 是資料。

⚠️ **範例檔在 `%USERPROFILE%\OneDrive\Desktop\PMIS範例\…`,不是 Desktop 直接下**
(記成後者會找不到,`compare-all.js` 也是走 OneDrive 那條)。
⚠️ 饒平案的決標公告**沒有契約工期**(B7 空),所以那一案驗不到直線推算,
要驗得另外把 B7 填進去(或換一案)。
