SP1(工程基本資料)開發期間對 `docs/samples/決標公告/` 28 份真實樣本的實測結論。屬 [[supervision-report-pipeline]]。

## 決標公告 PDF 的版面事實

政府電子採購網「友善列印」版,固定兩欄表。用 pdfjs 的 item 座標分欄:
- `x < 45` 區塊名直排字(機/關/資/料)、`45 ≤ x < 130` 標籤欄、`x ≥ 130` 值欄
- 同一列標籤與值的 y 座標差 1~3px,需 **±3 容差**合併
- 標籤過長會換行,續行 label 相同但 value 為空 ⇒ 取值必須找「第一個**有值**的列」

5 個錨點在 28/28 皆命中:`標案名稱`→工程名稱、`機關名稱`→主辦機關、`標案案號`→工程編號、`總決標金額`→契約金額、得標廠商(見下)。

**得標廠商不必然是「投標廠商1」**——28 份裡有 4 份不是(仁德第 2、四湖永慶第 3、豐榮第 2、鹿場第 3)。必須掃 `投標廠商N` 群組取 `是否得標 = 是`。後段「決標品項」區塊也有 `得標廠商` 標籤,但實測 28/28 的 `投標廠商1` 都早於第一個 `廠商名稱`,不會污染。

**標案案號格式各機關自訂**,不得驗證或推導:`1150113`/`A1150608`/`TKPS-A1150603`/`DRJH-1140923`/`ywjh11504`/`114-17`/`115-4`。

**PDF 字型把 3 個漢字映到 CJK 部首補充區,NFKC 還原不了**(NFKC 只處理 U+F9xx 相容漢字):
- ⺠ `U+2EA0` → 民 `U+6C11`(225 處 / **28 份全中**,「國民小學」)
- ⻑ `U+2ED1` → 長 `U+9577`(90 處 / 21 份)
- ⻄ `U+2EC4` → 西 `U+897F`(40 處 / 11 份)

不還原的話與 PMIS 主檔(標準碼位)比對會**每次都判不一致**,且錯字寫進正式報表。已在 `rowsFromItems` 修掉(刻意不動 `extractPages`,那支被廠商施工日誌讀取器用著)。

## 聯絡資訊(2026-08-02 補測,28 份全量)

這 5 個標籤**每份都恰好出現一次**,故用 `firstValue`(完全相等比對)即可,
不需要像得標廠商那樣掃 `投標廠商N` 群組:

| 標籤 | 命中 | 用途 |
|---|---|---|
| `聯絡人` | 28/28 | 學校聯絡人姓名 |
| `聯絡電話` | 28/28 | 學校聯絡人電話(含分機,如 `(05) 7882017 # 14`) |
| `機關地址` | 28/28 | → `schools.address` |
| `廠商電話` | 28/28 | 廠商聯絡人電話 |
| `廠商地址` | 28/28 | → `vendors.address` |

**兩邊不對稱,且不可能補齊**:決標公告**沒有廠商聯絡人姓名這個欄位**。
廠商聯絡人因此只有電話、姓名為 null。別為了「補齊」拿廠商名稱去頂——
已寫成測試釘住,以免日後被當成 bug 修掉。

`廠商電話`/`廠商地址` 緊接在「是否得標=是」那家之後,得標廠商排第 2、第 3 家的
那 4 份(仁德/四湖永慶/豐榮/鹿場)實測也不會貼到落選廠商身上。

地址值內含 PDF 分欄造成的空白(`655 雲林縣 元長鄉 元西路76號`),**照抄只 trim**——
自行合併等於編造格式,而承辦人本來就能手改。

### 自動帶入的鐵則:只補空缺,絕不覆蓋

`POST /api/schools/:id/seed` 與 `/api/vendors/:id/seed`:聯絡人只在「一筆都沒有」時補、
地址只在原本是空的時候填。**決標公告是決標當下的快照,承辦人維護過的值較新。**
若每解析一次公告就把承辦人改過的值打回舊值,而且沒有任何提示,沒人會發現。
同一所學校承接兩件工程會解析兩次公告,故必須冪等(不得長出第二筆聯絡人)。

## 值得記住的 bug 型態(SP2/SP3 會再遇到)

1. **「靜默降級」與「假成功寫髒資料」差一個數量級**,而分辨兩者要跨層追。例:開工日期格式錯 → `isoToExcelSerial` 回 null → COM driver 對 null 走 `ClearContents` → B8 空 → `=B8+B7-1` 拿空白當 0 算出 119 → 寫進 DB 的是 `1900-04-28` 加一個 200 OK。以為是 null,其實是編造的日期。
2. **驗「值轉成數字後是什麼」不等於驗「值本身是什麼型別」**。`String(['3057698'])` 是 `'3057698'` 會通過數值驗證,但 pg 送給 numeric 的是 `{"3057698"}` → 22P02,且發生在檔案已落地之後。需要 `isScalar` 型別守門。
3. **兩個「各自影響為零」的延後項可能在接縫處成立**。上面第 2 點就是「路由驗證器不驗型別」與「PS 的 `@($op.value)` 對陣列會 splat」的交集。
4. **單元測全綠不代表功能會動**。SP1 有 288 條綠燈測試,但沒有一條碰到真正的 Excel 寫入路徑(純函式測碰不到 COM、路由測把 `fillTemplate` mock 掉了),所以 `excel-com-driver.ps1` 那個會讓 SP1 100% 失效的 bug 一路潛伏到端到端測試才現形。
