2026-08-01 實測。起因:使用者想把「上傳開工報告表 → 與決標公告不符就跳警告 → 相符則更新工程資料並歸檔」做進 SP1,
問「裝 OCR 可以嗎?」。實測後**使用者決定先跳過此功能**,後續改走「像施工日誌一樣出一個讀取器」的路線(見結尾)。

## 技術可行性:零安裝成本(已驗證)

本機 Windows 11 + PS 5.1 實測,**全部走 Windows 內建 WinRT,不需裝 Tesseract/poppler/ImageMagick/Ghostscript,不需連外**:

- `Windows.Media.Ocr.OcrEngine` — `AvailableRecognizerLanguages` 含 `zh-Hant-TW`(繁中),且是 `TryCreateFromUserProfileLanguages()` 的預設。`MaxImageDimension` = 10000。
- `Windows.Data.Pdf.PdfDocument` — PDF 轉圖也是內建,`RenderToStreamAsync` + `PdfPageRenderOptions.DestinationWidth`。
- 串接:StorageFile → PdfDocument → PdfPage.RenderToStreamAsync → BitmapDecoder → SoftwareBitmap → OcrEngine.RecognizeAsync。
- **PS 7 載不動 WinRT 型別**(`Unable to find type`),必須用 `powershell.exe`(5.1)——與 [[xlsm-excel-com-findings]] 同一條路,專案本來就綁 PS 5.1。
- WinRT async 在 PS 5.1 要自建 `Await` helper(`System.WindowsRuntimeSystemExtensions.AsTask` 反射取 generic/action 兩種多載)。
- `PdfPage` **沒有 `Close()`**,要用 `Dispose()`。
- 效能:2200px 寬渲染下 **2.5–5 秒 / 2 頁**。24 份跑完約 2 分鐘。

## 逐欄辨識率(2026-08-01 補量,以決標公告權威值為真值,24 份全量)

| 欄位 | 2200px | 3400px | 聯集 2200+3400 |
|---|---|---|---|
| 主辦機關 | 88% | 88% | **88%** |
| 工程名稱 | 75% | 79% | **83%** |
| 契約編號 | 71% | 75% | **79%** |
| 契約金額 | 67% | 67% | **71%**(國字大寫案例被低估) |
| 決標日 | 58% | 63% | **63%** |
| 合計 | 72% | 74% | **77%** |

**多解析度聯集是唯一實測有效的調校手段**:2200+3400 取聯集 72%→77%;
**加第三個解析度(1500px)增益為 0**,成本卻多 50%,故只跑兩個。
改善非單調(四湖跳遠場在 3400px 多讀 4 欄、東榮國中反而少 2 欄)——
每份文件最佳解析度不同,這正是聯集有效的原因。
聯集只在**預填**情境正當;用於裁決會虛增信心。

**標籤變體幾乎沒用**:24 份中僅元長廁所一份使用變體(`契約約定工期`/`開工日期`)。
列入是補完整性,不是提辨識率——別再為此反覆調整。

**硬天花板是手寫**:橋頭/僑美/大勇的工期欄,任何解析度與標籤都讀不到。

真值比對為**下限**:未命中可能是 OCR 錯,也可能兩份文件本身確實不同(而後者正是要偵測的)。

## 契約工期單欄:不足以做自動比對(24 份全量實測)

拿 `docs/samples/開工報告表/` 全部 24 份 PDF 跑 page 1,對照 spec §4.3 有真值的 13 個工程,**只看契約工期**:

| 判定 | 工程 |
|---|---|
| ✓ 正確 6 | 大美 90、元長廁所 120、元長鋪面 60、東榮廁所 160、東榮丹娜絲 60、明禮 160 |
| △ 值對但與標籤斷開 1 | 鹿場 160(數字落在離「日曆天」一行遠的地方) |
| ✗ 錯字 3 | **南陽 150→`_J50_`**、**石龜 120→`__J_?O_`**、**豐榮 160→`一』一一`** |
| ✗ 完全沒讀到 3 | 橋頭 180、僑美 150、大勇 90(推測為**手寫**填入,OCR 讀不到手寫) |

**直接可用 6/13 = 46%**,而契約工期正是最關鍵、最需要人工的那一欄。

### 三個結構性障礙(不是調參數能解的)

> ⚠️ **第 1、2 點在 2026-08-02 被實測推翻**,見 [[sp1b-ocr-geometry-findings]]。
> 錯位不是 OCR 的性質,是我們**自己把座標丟掉**造成的(driver 只取 `$ln.Text`);
> 而「版面不統一所以座標規則無法通用」預設了座標規則必須是絕對版面。
> 改用**相對幾何**(值 = 標籤右側同列最近的框)後,四種版面是同一條規則。
> 第 3 點(國字大寫)仍成立,已由 `parseMoney` 處理。

1. ~~**label 與 value 在純文字輸出裡完全錯位。**~~ OCR 按視覺行掃,表格的標籤欄與值欄被打散。
   例:南陽那份「工程地點」四個字出現在地址**後面**一行;「契約編號」「契約金額」兩個標籤擠在值後面。
   ——**現已改依座標配對,此障礙不存在。**
2. ~~**開工報告表沒有統一版面。**~~ 決標公告能做座標分欄是因為它是政府電子採購網「友善列印」固定版面
   (見 [[sp1-award-notice-findings]]);開工報告表每所學校格式都不同,絕對座標規則無法通用。
   ——**但相對幾何可以**,且 24 份全適用。
3. **契約金額形式不一致。** 鹿場寫「新台幣:貳佰捌拾壹萬肆仟叁拾貳元整」(國字大寫),決標公告寫阿拉伯數字
   → **逐字比對必然誤判**。

其他次要事實:Windows OCR 對中文會**逐字插入空格**(「工 程 名 稱」),需正規化。
印刷體欄位(工程名稱、契約編號、開工日期)辨識良好,問題集中在填寫欄。

## 結論與決策

**技術上 OCR 完全可裝,但不該讓它下裁決。** 若讓 OCR 直接判「與決標公告不符」,
南陽案會因 `_J50_` 跳出假警告,承辦人就去請廠商修正一份其實正確的文件。
**假警報比沒警報更傷**——幾次之後承辦人學會直接按掉警告,功能等於白做。
曾提議的折衷是「OCR 只做預填候選值、承辦人逐欄確認後才比對」。

> ⚠️ **本段原記「使用者 2026-08-01 決定此功能先跳過、改走固化讀取器」,該決定當日稍後即被推翻。**
> 同日 SP1B spec §9 明訂「不做固化讀取器,本 SP 走 OCR 預填＋人工確認」,並已於 2026-08-01 完整實作完成
> (分支 `sp1b-kickoff-report`,25 commits)。讀取器路線僅在「日後要求廠商交電子檔」時才值得重新評估。
> 實作後的真實能力與限制見 [[sp1b-kickoff-report-implementation]]。

**技術結論仍然成立且已被實作驗證**:OCR 只作預填不作裁決。
實際做法是「讀不到留空、承辦人逐欄確認或修正、無硬錯才歸檔」,
且「讀不到」在架構上不可能升級成擋人的硬錯(`missing` 結構性不進 `hardErrors`)。

## 2026-08-10 追加:契約工期那一欄的兩個坑(已修)

**① 日曆天/工作天是並列的勾選項,不是「哪個詞出現就是哪個」。**
表單版面是「□日曆天 □工作天」,24 份實測 **17 份的 OCR 文字兩個詞同時出現**。
舊版 `parseDuration` 用「哪個詞存在」判、且工作天排前面,那 17 份一律判成工作天。
改用「數字緊接哪個詞」;兩個都在又沒有數字緊接任一個時**回 null 不猜**
(承辦人可在畫面的「工期基準」欄自己選,`projects.duration_basis`)。

**② 民國年被當成工期天數。**欄位配對常只抓到後半段——台西實際餵進
`parseDuration` 的是「工作天115年10月28日前竣工」,那個 115 是**民國年**,
被當成 115 天(真值 120);橋頭讀成 116 天(真值 180)。
`120 → 115` 看起來完全像個合法工期,不會有人察覺。修法是先把日期片段整段移除
再抓數字。

⚠️ **`compare.js` 對契約工期只計命中率,拿它判斷好壞會得到反向結論**:
修完之後命中率從 18/23 掉到 15/23,看起來像退步,實際上是三份「命中但錯」的
改回誠實 null(元長、古坑棒球場宿舍的原文根本沒有工期數字),另三份從錯值改成
正確值。這一欄沒有自動真值(決標公告不含工期),只能人工看原文。

**逐欄基準線(preset5m@3400,23 份有真值)**:工程名稱 19/4/0、契約編號 20/0/3、
契約金額 21/0/2、決標日期 17/1/5、主辦機關 18/1/4、縣市 22/0/1、
契約規定開工日 23/0/0、契約規定竣工日 23/0/0。
使用者回報「契約編號讀取率偏低」「中文大寫金額難讀」,但實測兩者分別是
87%(0 錯 3 漏)與 91%(0 錯 2 漏),**都沒有錯值**——要再投入前先確認他遇到的
是不是這 24 份以外的文件。
