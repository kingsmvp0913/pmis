2026-08-08 使用者問「我說的用程式跑完文件產生新監造報表並和現有監造報表比對這個有做了嗎」
——**當時還沒有**(前面幾輪都在補讀取器/修驗證層/量 OCR)。這一則記的是當場做出來的基座、
第一批結果,以及它立刻抓到的一個 production bug。

## 2026-08-11 乾淨重跑的結果:**與 8/8 基準逐案完全相同**

42 案(2 案失敗是既有的「沒有讀得動的日誌」:忠信、永隆):
**一致 7425、只有人工 2133、只有系統 645、矛盾 163**——
逐案比對「項目一致/一致/只有人工/只有系統/矛盾」五個數字**一個都沒變**。

這正是要的結論:那一輪做的全是版面(項次前綴、刪列、欄寬、表報編號、天氣、
預定進度),**一格數值都沒動到**。要驗證「版面改動有沒有誤傷數值」,這支就是那把尺。

## ⚠️ 重跑 44 案之前一定要先刪掉 `compare-all.json`

`compare-all.js` **是可續跑的**:開頭讀既有的 `compare-all.json`,
`results[案名] && !error` 就 `continue` 跳過。所以「改完程式重跑一次看有沒有變」
**根本沒有重跑**——它把幾天前的舊結果原封不動再印一次,合計數字當然一模一樣,
而那看起來正好像「我的改動沒有影響數值」這個預期中的結論,**極容易誤判**。

2026-08-11 就這樣誤判過一次:合計印出「一致 7425、矛盾 163」與舊紀錄完全相同,
差點當成驗證通過;實際 `raw` 欄裡的 `pmis-built-<epoch>.xlsm` 全是三天前的。

正確做法:`mv compare-all.json <備份>` 之後再跑,並且**跑完核對 `raw` 裡的
建置時間戳是不是當天的**。

## ⚠️ 失敗會累積殭屍 Excel,而症狀看起來像「程式改壞了」

一案失敗會留下一個沒有視窗的 `EXCEL.EXE`;累積之後**後續每一案都被
`RPC_E_CALL_REJECTED` 拒絕**,於是失敗案越來越多。2026-08-11 實測跑完一輪
殘留 13 個,而且單獨重跑那一案也「穩定失敗」——看起來完全像是剛改的程式弄壞了
(那次剛好動到 49 項的擴列,嫌疑更大)。**把 EXCEL 進程全部殺掉之後同一案立刻成功,
結果與舊基準完全相同。**

診斷順序:單獨重跑仍失敗 → **先 `Get-Process EXCEL` 看有沒有殘留**,再懷疑程式。
殺之前先看 `MainWindowTitle`,有視窗的是使用者自己開的檔案,不能殺。

不過那一次殭屍只是放大器,**真正的成因是單案耗時被拉長一倍**:天氣寫入原本是
逐格 `setCell`(每天兩道),簡易棒球場 87 天 → 指令數 11 → **185**、耗時 12s → 24s。
**每個 setCell 是一次 COM 往返**,而 COM 偶發拒絕的機率隨往返次數與時間上升。
改成整段 `setRange` 之後 15 道、14 秒(`b8064f6`)。
**教訓:凡是「逐日/逐項」的寫入,一律出 setRange,不要逐格 setCell。**

## 基座:`data/parser-tools/build-and-compare.js`

`node data/parser-tools/build-and-compare.js "<案資料夾>" [--keep]`

**走的是與 routes 完全相同的產線程式碼**(不是另寫一套):
- SP1 `award-notice.readAwardNotice` → `project-basics.basicsToOperations`
- SP2 `budget-sheet` + `contract-items.selectSheets` → `itemsToOperations`
- SP3 該廠商的 `.pmisparser.js` → `daily-log-write.daysToOperations`
- `template-engine.fillTemplate(公版範本 → 新檔)`(**真的走 Excel COM**,一案約 12 秒)
- 再用 SheetJS 讀回新檔與該案的人工 `監造報表.xlsm` 逐格比

立場沿用 `check-against-truth.js`:**人工報表也可能有錯**,只列兩邊的值、不算準確率。
兩個必要的雜訊處理(踩過才知道):
1. **人工報表的「(合計)/每日實際進度/預定進度」是公式列**,每一欄都有值。不排除的話
   「人工有值的天」會變成整條 753 天的範圍(實測 594 天 vs 實際 58 天)。
2. **範圍符號 `~` vs `-`** 只在這支工具裡視為等價(人工打「(壹-伍)」、經費總表打「(壹~伍)」)。
   刻意不併進 production 的名稱正規化,理由同 [[truth-layer2-items-findings]]。

## ✅ 已修的 production bug(範本,commit `e81e587`)

`每日施工紀錄` 的每一欄都是這種公式:

```
B2 = INDEX(契約詳細價目表!$1:$1048576, MATCH(契約詳細價目表!B2, 契約詳細價目表!B:B, 0), 2)
```

**關鍵觀察:查找欄與取值欄是同一欄** —— 用 B 欄的值去 B 欄找、再取回 B 欄,
這是**恆等映射**,繞 MATCH 一圈毫無作用(重複名稱也一樣,因為條件就是「等於」)。
所以正解不是把 MATCH 修好,而是**把整層 MATCH 拿掉**。

`MATCH(..., 0)` 會啟用萬用字元,`~` 是跳脫字元:
- **實測只有 `~` 會壞**(查不到自己 → #N/A)。`*`/`?` 反而通常匹配得到自己
  (`?` 匹配任一字元、含 `?` 本身),但**可能先命中更前面的同型名稱 → 靜默取到別列的值**,
  那比空白更危險。記憶前一版寫「`*`/`?` 也會變空白」是錯的。
- 數量照樣寫進去 → 報表上是一列**有數量卻沒有名稱**的項目。
- 影響面:49 案答案卷裡有 **57 對**名稱含範圍符號。

**實際影響面比原先記的大:371 格,分兩類**(用 `scan-match.js` 掃出來的):
1. **恆等自我查找 340 格** —— 每日施工紀錄 `A2:F37`(216)+ 監造報表 `A/B/G/H 10:40`(124)。
   改成 `=IF(契約詳細價目表!B2="",NA(),契約詳細價目表!B2)`。
   **`NA()` 不可省**:範本現況是未使用的列整片 `#N/A`,直接引用會變成 0 → 空白列印出一排零。
2. **真查找 31 格** —— 監造報表 `I10:I40`(當日數量:拿項目名稱去每日施工紀錄 B 欄找列)。
   這條不能改成引用,改成把查找值跳脫:
   `SUBSTITUTE(SUBSTITUTE(SUBSTITUTE($B10,"~","~~"),"*","~*"),"?","~?")`(**`~` 必須排最前面**)。
   ⚠️ 名稱欄修好後這條仍會獨立失效,測試要分開斷言。

其餘 MATCH 都是常數字串(`"工程編號"`)或日期參照,不受萬用字元影響,不必動。

改範本的工具:`data/parser-tools/fix-template-formulas.js` + `.ps1`(可重跑)。
寫入用 `.Formula` 而非 `.Value2` —— Value2 的字串 setter 走**系統地區的 list separator**,
在用 `;` 的機器上會把公式寫壞。先 SaveAs 暫存檔、成功才覆蓋範本,中途失敗不會留半改的範本。

回歸測試在 `app/tests/template-engine.integration.test.js`(受 `SP0_SKIP_EXCEL` 管)。
⚠️ 改公式會讓既有的 `insertRowsBelow` 測試紅(它斷言 `/INDEX\(契約詳細價目表/`),已改成
斷言位移後的列號 `/契約詳細價目表!A33/`。

**驗收(永定案端到端)**:194 格一致 / 62 格只有人工有 → **256 格一致 / 0 格落差**。
194+62=256,那 62 格正是 `~` 名稱害的。

## ✅ Excel COM 連續執行 4 成失敗:根因已量出並修掉(commit `58e84e1`)

**根因是兩種 COM 競態,不是殘留 EXCEL.EXE**(driver 舊註解把成因歸給殘留實例,
那不是唯一原因——實測失敗當下沒有殘留進程):

1. `Workbooks.Open` **回傳了 workbook 物件,但 `.Worksheets` 是 null**(ReadOnly=False)
2. `Workbooks.Open` 直接拋 **RPC_E_CALL_REJECTED**(0x80010001,Excel 忙碌)

**能量到根因的前提是先做兩件事,缺一不可**(這是本次最可複用的一課):
- **stdout 編碼改 UTF-8**:`[Console]::OutputEncoding = New-Object System.Text.UTF8Encoding $false`。
  不做的話 COM 的中文錯誤傳回 Node 是亂碼(`���i�b�Ȭ� Null`),根本不知道發生什麼事。
- **分步命名**:Open 之後才 null 的話,後面一律是同一句「不可在值為 Null 的運算式上
  呼叫方法」,看不出斷在哪。對 `$wb`、`$wb.Worksheets`、`$ws`、`$cell` 各給一句訊息。

**修法:在同一個 Excel 實例內重開**(最多 4 次、遞增退避),不要讓整個 job 失敗、
由 Node 層重新 spawn PowerShell + Excel —— 後者正是 40% 失敗的來源:外層重試每次
都要付整個 Excel 啟動的代價,卻沒有解決競態本身。

**壓力驗收**(案間間隔從 8 秒降到 1 秒,比原本更嚴苛):
**44 案 0 案倒在 Excel**(修前 17 案),批次工具那層「整案重試」一次都沒觸發。
最終 42/44 成功,剩下 2 案是刻意不接的忠信(掃描 PDF)與永隆(`.doc`)。
⚠️ **RPC_E_CALL_REJECTED 必須在迴圈內 catch**:`$ErrorActionPreference` 是 `Stop`,
不接住的話第一次就逃出迴圈,重試等於沒寫(我第一版就是這樣,白跑一輪)。

### (以下是修之前的量測,保留當作根因的證據)

`data/parser-tools/compare-all.js` 一口氣跑 44 案時,**20 案倒在
「Excel 驅動重試 3 次仍失敗:不可在 Null 的運算式上叫用方法」**。
關鍵證據:
- 失敗**散佈在整個序列、成功失敗交錯**(第 1、11、12、13、15、18…),
  不是後段累積劣化 → 是隨機的。
- **失敗案單獨重跑就成功**(逐一驗過後埔、德信、永定)。
- 事後查沒有殘留 `EXCEL.EXE`,所以 driver 註解說的「殘留實例」不是唯一成因。

`fillTemplate` 的全域序列化 + 3 次重試 + 2 秒 delay **擋不住**:三次全撞的機率有 4 成。
當時想到的「調長 delay / 加大次數」是猜的——**先診斷是對的**,因為真正的競態有兩種,
其中 RPC_E_CALL_REJECTED 再怎麼加長外層 delay 都只是碰運氣。

批次工具的繞法(修 driver 前做的,現在 sleep 已降到 1 秒當壓力測試):
案間 sleep、撞到 Excel 卡頓隔 15 秒整案再試一次、
**只跳過「已成功」的案**(失敗的一定要重跑,因為多半不是資料問題)。

## 全案跑完的結果(2026-08-08,44 案)

`data/parser-tools/compare-all.js` = 批次跑 build-and-compare 並收成一張表
(結果留在 `compare-all.json`,可中斷續跑)。選案條件:有讀取器的廠商 + 有人工監造報表
+ 有經費總表 + 有決標公告。**40/44 案成功**;剩 4 案:忠信(掃描 PDF)、永隆(`.doc`)
兩個是刻意不接,永定與簡易棒球場是 Excel 卡頓(永定單獨跑過,0 落差)。

**「只有人工有」不可以不分日期地一起算** —— 這是第一版分析踩的坑:
好幾案系統一天都沒讀到(日誌是掃描 PDF 或樣本裡根本沒有),整案的格自然全落在
「只有人工有」,和讀取器逐格漏讀是完全不同的問題。切開後才看得到真相:

- 日誌沒讀到的天上:**2318 格**(覆蓋率問題,不是讀取器讀錯)
- 兩邊都有的天裡:一致 **6969**、只有人工 1993、只有系統 645、**矛盾 163**

### 矛盾 163 格逐案看完的分類(這是最重要的結論)

**約 142 格(87%)是「費用項目」,不是主體工程項目讀錯。** 費用項目
(職安衛管理費/品管費/包商管理費/保險費/營業稅)在人工報表是**按天平均攤**的,
施工日誌上根本沒有這種紀錄,兩邊必然對不起來。而且**系統這側三種寫法都出現過**:

| 案 | 人工 | 系統 | 性質 |
|---|---|---|---|
| 文安(54) | 0.0109 | 0.0028 | 都是比例,分母不同 |
| 林內射箭場(72) | 0.0111 | 56.53 / 432.28 | **單位就不同**:人工比例、系統金額 |
| 石龜C2(12)、竹崎(4) | 比例 | 比例但值不同 | 同文安 |

**真正「主體工程項目數字不同」的只有約 20 格**(台西外牆磁磚敲除 52.28/63、
竹崎圍網 40/124,以及 4 案各 1–2 格)—— 對照 6969 格一致,約 **0.3%**。
**讀取器對主體項目幾乎不會讀錯**;要再投資,投在費用項目的製表慣例上,不是讀取準確率。

還有一類與數字無關的落差:**名稱差一個字**。文安的「包商管理費及利潤(**約**壹*7%)」
人工報表少了「約」,林內三個費用項目名稱也對不上 → 光這個就製造 56+56、108 格
「只有一邊有」。

費用項目的攤提也是「只有人工有」的成因之一,但**只解釋 17%**,不是主因——
主因是日誌覆蓋率(見上)。別把它當通則(第一版分析在這裡估錯)。

## ✅ 費用項目改由系統推算(commit `33deade`,使用者拍板)

**這是 163 格矛盾裡 87% 的解法。** 決策內容(用選項問出來的,不是我自己決定的):
- 費用項目由**系統自動平均分攤**,不等承辦人給公式。
- 分攤到**工期每一天**(不是只有施工的天)。
- **報表版面完全不動**,標示只放在系統畫面上。

⚠️ **這不是重現承辦人的算法**——他們的公式推不出來(文安工期 56 天,平均應是 0.0179,
實際填 0.0109),而是**另定一個講得清楚的規則**。數字會跟舊報表對不起來,
但講得出根據。下次有人問「為什麼跟以前不一樣」,答案在這裡。

**每天 = 契約數量 ÷ 契約工期天數**,鋪滿開工日到竣工日。三個實作要害(踩過才知道):
1. **分母固定用契約工期,不是「目前收到幾天日誌」**——日誌分批交,用已收到天數當分母,
   每收一批先前寫進去的數字就全部作廢要重算,承辦人看到的數字還會一直變。
2. **費用列的 setRange 必須排在主範圍之後**:主範圍是整塊矩形,會把涵蓋到的費用格
   寫成 null,順序反了等於白算。
3. **一列一道 setRange,不是整塊**:費用項目未必連在一起,而涵蓋到施工項目的矩形
   會把**先前批次**寫進去的進度清成 null。

沒填竣工日期時不推算、維持原行為——推算費用是輔助功能,不該讓一份本來寫得進去的
日誌整份卡住。費用項目的判定 `isFeeItem` 從 `budget-sheet` 共用(帶前綴的 `A.貳` 也認得),
畫面文案由 `feeItemsPlan` 產生,與實際寫入同一個來源、不是前端寫死的字串。
