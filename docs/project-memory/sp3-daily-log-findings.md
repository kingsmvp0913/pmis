2026-08-05 完成 SP3(施工日誌 → 每日施工紀錄)。驗證清單 46 條扣掉客戶勾除的 7 條

## 三家讀取器的欄位落差(決定了規則能不能照抄)

dailyRows 欄位三家一致(8 欄:項次/工程項目/單位/契約單價/契約數量/本日完成數量/
本日完成金額/累計完成數量),但 header 差很多:

| 欄位 | 金大(80天) | 晉林(105天) | 摯東(31天) |
|---|---|---|---|
| 天氣 | **全 null** | 晴 | 晴 |
| 星期 | 星期三 | 三 | **全 null** |
| 預定/實際進度 | **全 null** | 0.75/0.73 | 0.477/0.4771 |
| 本日累計金額 | 10400.248 | 22766.24 | **全 null** |
| 出工總人數 | 全 null | 全 null | 全 null |

**「抽不到」不等於「沒填」**:照 A2(天氣未填=硬錯)實作的話,金大這家 100% 過不了。
規則:某欄位**整份都缺** → 判定格式不提供,跳過並列入 `skipped`;只有部分天缺 →
才是真的漏填。只有一天時兩者分不出來,分不出來就不放行。
**skipped 一定要回傳並顯示**——靜默跳過會讓承辦人以為驗過了(同 SP1B 的教訓)。

**四條根本驗不了**,明講而非假裝通過:B5 完成百分比、E7 契約複價(三家都不提供該
欄位)、F2 累計金額不回退(無獨立來源,推導值天然不回退)、摯東不給本日完成金額時
連帶的 B3/B4/C2。

## 跨批次累計(最容易漏掉的一條)

施工日誌分多批提交,而累計欄位是**跨批累積**的。驗證層若每批從 0 起算,
B3(累加金額 vs 累計數量×單價)在每一批的第一天都必然誤判——**承辦人送第二批
就被擋死**。`validateDailyLog` 因此收 `prior` 參數,由 routes 從 `daily_records`
算出「這批最早日期之前」的累計。金額用「數量×契約單價」還原(daily_records 只存數量)。

同理:落庫時**只清這批涵蓋的日期**,不清整個工程——分批提交是常態,清掉別批等於
把已寫入的進度弄丟。附件則每批都留(與開工報告表的覆蓋規則不同):日誌是累積的
來源憑據。

## 兩個「看起來正常但全錯」的坑

1. **浮點誤差**:晉林實測跑出 81 個「累計 1.0000000000000002 超過契約數量 1」的
   假硬錯。所有數值比較(含大小比較)一律走 0.01 容差,否則真正的超量
   (摯東 270 > 266)會被淹掉。
2. **DATE 不可用 `toISOString()`**:pg 把 DATE 解析成**本地時區**午夜的 Date,
   轉 UTC 會讓台北時間整批日期倒退一天,而報表上只看得到進度整體平移。

## 寫入定位

`每日施工紀錄!J1 = 工程基本資料!B8`(開工日)、`K1=J1+1`…到 ACH(約 753 天),
故某天寫哪一欄 = `J + (填報日 − 開工日)`。列則依契約表項次順序(該分頁靠 MATCH
拉同一順序),第 2 列起。一天一格 setCell 的話 80 天 × 39 項會生出 3120 道指令,
故一律組成**單一 setRange**;範圍內的假日欄寫 null,不可把後面的資料往前擠。

**共通結論**:剩餘硬錯經逐條查證**大多是廠商資料問題**,不是讀取器。
多欄表格 PDF 一律走 `ctx.filetypes.extractItems`(座標版,本輪新增)——
抽成文字會把數字黏成「1.002,500.00」,還原不回欄位。

✅ **2026-08-06 已修**(金大 v1.1.0,分支 `fix/jinda-parser-coordinates`)。當時的漏網情況:四個 PDF 讀取器裡
(金大/陳宏鈞/富森/展翔)只有 `jinda.pmisparser.js` 仍走純文字 `extractPages`,
其餘三家都已是 `extractItems`。後果實測:2026-06-04 項次 8 該列廠商只填了一個
`62.0`,座標 x=456 落在**金額欄(群集 x≈430)與累計欄(群集 x≈490)之間的無人區**,
而「本日完成數量」欄(x≈360)在該列是空的——讀取器卻靠「該列第一個數值」把它
塞進本日完成數量,再生出一個 A8 硬錯「本日有施工但金額讀不到」。**這個硬錯的
成因是讀取器猜錯欄,不是廠商漏填**;正確行為是座標對不上任何欄就標為無法判讀,
交給承辦人,而不是猜。1280 列只中 1 列,但靠列序推斷是系統性風險。

修法(可移植到其他讀取器):單一 item 常橫跨多欄(`"2250.00    1.0    "` 同時裝著
金額與累計),光有 item 的 x 不夠——`extractItems` 已補上 pdf.js 的 `w`,用
`w / s.length` 推每個字元的 x,再取 token 中心判斷落在哪個表頭欄界 `[x, x+w]`。
**中心落在欄與欄之間就不指派**,留 null 讓 check-parser 的完整性關卡看得見。
契約單價/數量仍走 token 順序:表頭「單位 契約單價 契約數量」是單一 item,取不到欄界。
修後硬錯 8 → 6(A8/F4 那組假硬錯消失),缺漏維持 0 列。

**gen-vendor-parser skill 補了三道關卡**:單位改走白名單(禁樣式判定,那正是
金大 RC bug 的來源)、交付前必跑 `app/scripts/check-parser.js` 的完整性與跨層驗證。

## 原始問題:金大的讀取器品質(已修)

金大那份跑出 B3:318、B4:80、A7:160、J2:160。追下去根源**不是廠商填錯,是讀取器**:
項次 7、8 的單位被讀成 `"RC"`(項目名稱被吃進單位欄)、契約數量與單價讀成 null;
`header.本日累計金額` 讀出 `10400.248`(金額不該有小數)。這家的日誌現在送進來一定
過不了。**已修**:單位判定改走白名單,硬錯 730 → 8、完整性缺漏 160 → 0。

## SP3 自己的一個邊界 bug(2026-08-08 久木案發現,**尚未修**)

`daily-log-validate.js` 的 H1 用 `toPct = v => Math.abs(v) <= 1 ? v*100 : v` 把
比例制與百分數制統一。**實際進度剛好到 100%(1.0000007)時會落到 `> 1` 那一邊**,
被當成「1%」去跟預定的 93.6% 比,噴出假的「實際落後預定超過 10%」。
久木完工前兩天中招。凡是進度跑到 1.0 以上一點點的案子都會中。
只是軟警告,但它出現的時機正好是**每個工程的最後幾天**,誤導性高。
沒有動它是因為那是跨階段的檔(補讀取器的任務不改 SP3),要修請單獨處理。

**同一條 H1 的另一半(2026-08-08 宜謙案發現,同樣未修)**:`<= 1` 的那一邊會把
**真的只有 0.28%** 的進度當成「28%」。宜謙的案子開工頭幾天預定進度是 0.0003~0.9%,
於是「預定 0.24、實際 1.6」被判成落後 22 個百分點(1.6 − 24)。**每個工程的最前面
幾天都會中**,加上上面那條(最後幾天也會中),H1 實際上在工期兩端都不可信。
根治要讀取器回報單位(百分數 vs 比例),不能靠值域猜——0.5 到底是 0.5% 還是 50%
在數值上無從分辨。

## 項次的異體字會變成硬錯 E1(2026-08-08 宜謙案,**未修**)

同一個工程的兩份文件把費用項第三項寫成不同的字:發包後經費總表是「参」(U+53C2)、
簡易棒球場的日誌是「參」(U+53C3)。`contractByNo` 是逐字相等,`squash` 的 NFKC
**不會**把這兩個字折成同一個(它們是異體字不是相容字),名稱又剛好也不同
(「公共工程品質管制作業費」vs「工程品質管制作業費」)→ 名稱後備索引也救不了 →
**每天一個 E1 硬錯,86 天全擋**。宜謙其他 3 案兩邊都是「参」,所以只有這一案中。
不在讀取器修:項次是來源識別碼,改寫它等於把一種誤判換成另一種(下一案若兩邊
都寫「參」就反過來壞掉)。要修應該在比對層,把中文數字大寫的異體字
(參/参、佰/百…)正規化後再比,與 squash 的 NFKC 同一層。

## C1 沒有「費用項目」的分支,但 B2/F1/B3 有(2026-08-08 國謙案,**未修**)

`是費用項目` 會把 B2/F1/B3 降成軟警告(理由:費用項的「完成數量」各家語意不一),
但 **C1「累計完成數量超過契約數量」沒有同樣的分支**。國謙那家在費用項的完成數量欄
填的是**金額**(56.53 元,而契約數量是 1 式),於是每天 5 筆 C1 硬錯、42 天共 210 筆,
把真問題全淹掉。要嘛 C1 也跟著降級,要嘛三條規則一起改成「費用項只驗比例語意」。
