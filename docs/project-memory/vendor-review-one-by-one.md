## ⚠️ 最大的收穫:三種**我自己製造**的假訊號

第一家(長澤)一開就發現大半的「要看」不是讀取器的問題。做這類彙總表一定會踩:

1. **多份 fixture 串起來當一份驗**。那些檔多半是不同的案(長澤 pdf 是 2024 跳遠場、
   xls 是 2025 中和;正郁的成功/林內)或同一案的重疊載體(玉森三份互相涵蓋)。
   串起來後同一個項次裝著兩套項目,E4/E5/E6 整片爆掉。
   逐份驗:**長澤 5577→107、玉森 5221→0、東震 802→0、正郁 333→0、明德 82→2**。
2. **把不適用的規則算進總分**。`F4`(期末累計≠契約數量)在只涵蓋部分工期的樣本必然全滅
   (宜謙 pdf 1 天噴 F4:24);`A8/B3/B4/C2` 在**只有 1 天的樣本**也必然噴——
   SP3 的「整份皆空就跳過」要求 `days.length >= 2`(單天分不出「格式沒這欄」與
   「今天沒填」)。兩組都抽成獨立欄、**不參與判定但照樣印出來**。
3. **完整性也要逐份算**。「此格式不提供某欄」講的是**一份文件**提不提供;
   東震 pdf 沒有契約單價、xls 有,合起來算就變成「750 列缺單價」(明德同理 754)。

(第四種「零列會拿滿分」在 [[vendor-parser-coverage-plan]]。)

## ✅ 四支讀取器的真 bug——**四個都是「缺的不是列就是欄,不會有欄位變 null」**

- **長澤**:尾端 11 個是廠商「一次建好整個工期」還沒填的區塊,被當成 11 個
  「日期讀不到的天」。原判別要求「沒日期**且**整天沒填過東西」,而那些區塊的本日完成
  被公式帶進殘值。**乾淨的判別依據**:它們的預定進度來源是 `=+#REF!` → error cell 轉 null,
  而有日期的 101 天預定進度**全部有值,零重疊**。
- **陳宏鈞**:`groupRows` 用「第一個進來的 item」當帶的錨點,長名稱一換行錨點就被拉到
  名稱續行,契約數量(印在項次下方 5pt)超出容差 → **那一欄整份消失**。
  改錨在項次 id,容差 4→6(Δy 有 35 次在 −3.5~−5.6、逐頁不同;列距最小 12.8)。32→0。
- **明德**:兩聯**各壞一種**。第一聯用 x 界切「名稱 vs 值」,而界是 `min(表頭中心)-60`=37,
  名稱本來就長到 x≈170 → **名稱被截尾**(「…一底漆二」,來源其實是完整一行);
  又因 `!名.length` 擋住對稱收編,三行的名稱只留中間段。
  第二聯更狠:名稱在別帶時 `名` 是空的 → `if (!工程項目) continue` **把整列丟掉**,
  項次 3、7、26(最長的三項)每天都不見,**806 → 884 列**。
- **富森**:①「名稱片段歸給 y 最近的項次列」不夠——項次28 名稱跨四行、塊高 30pt 而列距
  13~26,最外那行離鄰居比離自己近 → 兩個項目的名稱黏在一起。改對稱配對,
  **並把優先權給「自己那列沒有名稱」的項次**(否則下一個項次先搶走一段)。
  ②**一天佔兩頁,續頁重印頁首卻沒有明細表頭** → 上界 Infinity,整段頁首黏進該頁第一個
  項次(61 天的項次31、8 天的「貳」)。上界改取表頭列與頁首標籤列中最低者,
  **但只看最上面那個項次列以上**——表尾註記也寫著「預定進度及實際進度」,
  不設這條會把上界壓到 y=161.9,整頁明細一列不剩。

📌 **四個 bug 的共同形狀:天數對、列數看起來合理、沒有任何欄位變 null。**
逐格比對與完整性統計都看不到;名稱健檢只抓到其中兩個(而且富森那個污染名稱
括號是平衡的,健檢也看不到)。**要抓得靠「跨份/跨聯比對」與「項次連續性」。**

### 三個「原本完全沒有防線」的事實(這是重點,不是規則本身)

1. **優和那種日誌 39 條規則一條都不觸發**。單位/數量/單價三欄全空 → `isCategoryRow`
   回 true → 整列略過。45 天可以一路寫進監造報表,**零錯誤零警告**。
   ⚠️ A9 只在「有列但全是大類列」時判;**整天 0 列是「沒施工」,不可判錯**——
   兩者只差在有沒有列,判錯會把嘉原(22 天空白)、利成(40 天空白)整類擋掉。
2. **名稱形狀健檢原本只在 `scripts/check-parser.js`**(開發用腳本),產線不跑。
   這輪修的四支讀取器壞法全是「名稱錯了但沒有任何欄位變 null」——**上線後一個都擋不住**。
   已搬進 daily-log-validate,check-parser 改成 require 同一份(留兩份必然漂掉)。
3. **久木的硬擋是假的**。`priorCum()` 只從**已上傳的** daily_records 推前期累計,
   前幾個月沒上傳就從 0 起算 → 155 筆 B3 假硬錯。

### 期初累計(`daily_openings` 表 + GET/PUT openings + 前端收合區)

- 後端 `validateDailyLog` **本來就吃 `prior` 參數**,缺的只是「沒上傳過的前期」入口。
- **整批覆蓋而非逐筆 upsert**:清空某一項時舊值會留在庫裡,畫面看起來清掉了、
  驗證仍用舊值,**而且不會有任何錯誤訊息**。
- GET 一律以契約表為骨架逐項列出(含還沒填的),只回已存的那幾筆會讓漏填的項目隱形。
- 金額用「數量 × 契約單價」還原(daily_records 只存數量),與既有 priorCum 一致。

## ⛔⛔ 最貴的一筆:展翔整個第二聯沒讀,而我把它記成了廠商的錯(`1d7d898`)

承辦人只說了一句 **「展翔的七月我看每天都是完整明細?你說的不完整是?」**——
系統讀出來是「整月只出現 2 個項目、每天 0.6 列、此格式不提供契約單價」。

**根因**:讀取器 v1.0.0 的檔頭斷言「第二聯沒有項目名稱,只有數量/單價/金額三組數字」,
據此**整個第二聯都不讀**。那個斷言是錯的——名稱就印在第二聯的 x=52,
而且**第二聯才是完整清單**(大類壹 + 項次 1~31 + 費用項 貳~陸 = 37 列),
第一聯只列當天施作的項目。改讀第二聯:37 列/天、缺欄位 0、硬錯 0。

### 我因此連錯三件事

1. 把「展翔 E4×3(單位 6/27 印 M2、6/28 起印 式)」登記成**來源缺陷**,
   並在逐家走查時拿去問承辦人、他還做了裁決。那是只讀第一聯造成的欄位落點錯誤。
2. 把「此格式不提供契約單價」寫進矩陣——第二聯有單價。
3. 用 D5 判它「當月最後一天不完整」,拿去當「要不要全面套用」的證據之一。

### 📌 通則(比這一支讀取器重要得多)

- **少讀整批列不會有任何欄位變 null、不會有任何錯誤訊息**,留下來的那幾列還完全自洽
  ——三道關卡與 42 條規則**一條都不會叫**。缺漏統計、名稱健檢、SP3 全部看不到。
- **要抓這一類,只能拿系統讀出來的東西跟紙本對「列數」。** 逐格比對抓不到,
  因為每一格都是對的。
- ⚠️ **讀取器檔頭裡「這一頁/這一欄不用讀」的斷言要當成可疑對象重驗**,
  那是唯一會讓整批資料無聲消失的地方。展翔、明德第二聯、富森續頁都是同一型。
- 📌 **承辦人打開檔案看一眼,勝過我跑三道關卡。** 這一輪兩次都是他先發現
  (新成的隱藏欄、展翔的第二聯)。**問他之前先確認「你看的是哪一份檔案」,
  他答得出來的東西是我驗不出來的。**

### 三個「單位欄含數字」的坑(修這支時踩到,別家也會有)

① 單位是「M2」「M3」時裡面有數字:欄界劃太左,那個 2 會被當成契約數量
   (項次7 契約 28 讀成 **2**,而 28.00 因為「先到先得」被丟掉);
   太右則單位「M」整格落進數值區、變 null(項次15)。**界要取兩個表頭中心的中點。**
② 一個 item 同時裝兩個數字(`1.00    253,106.00`)→ `w / s.length` 推字元 x 再取中心。
③ **補值不可以用「名稱非空」當前提**:名稱換行時值自己佔一列,那列名稱欄是空的。
