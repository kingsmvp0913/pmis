使用者桌面的 `%USERPROFILE%\OneDrive\Desktop\PMIS範例\模板\全案範例\` 有 **49 個完整案子**
（不是 `~/Desktop`，那裡只有 Caddyfile；實際桌面在 OneDrive 底下）。

**為什麼重要**：每案都附一份**人工做好的 `*_監造報表.xlsm`**——那是 ground truth。
這是目前唯一能打破 [[parser-pipeline-gaps]] 記的第二個結構性盲區
（驗收拿讀取器自己的輸出當基準，所以「讀錯但格式合法」永遠驗不出來）的東西。

**實測過的版面事實（2026-08-07）**：

- 49/49 案的成品 .xlsm 分頁**完全一致**：`封面 | 封面 (2) | 監造報表 | 工程基本資料 |
  契約詳細價目表 | 監造內容 | 每日施工紀錄`
- 49/49 案的「工程基本資料」分頁 A1..A10 標籤一致，**B1..B10 對得上
  `app/server/project-basics.js` 的 `CELL_OF`**，9 欄填寫率 **49/49 全滿**
  → 441 格答案可直接抽，不需版面偵測
- 開工日期存的是 Excel 日期序號（如 `45338`），不是字串

**各層樣本數**：決標公告 49/49、開工報告表 49/49、監造報表 49/49、
發包後經費總表 46/49、施工日誌 46/49（324 份：pdf 95 / xls 90 / xlsx 82 / docx 36 / xlsm 20）。
43 案五類齊全。

**未查證**：施工日誌有大量檔名帶「掃描」的巨檔（22MB～66MB），很可能沒有文字層、
現有文字抽取讀取器讀不了。動日誌那層之前要先分類文字型 vs 掃描型。

⚠️ **使用者的明確條件**：這些成品是人做的，**難免有錯**。比對結果**不得預設答案卷是對的**，
差異要兩邊的值都列出來讓人判斷，不能寫成「準確率」。
