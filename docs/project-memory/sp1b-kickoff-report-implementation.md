## 兩個只有端對端才抓得到的缺陷（單元測試結構上不可能發現）

> 第 1 點的根因在 2026-08-02 被更正：不是「抽取錯位」這種個案，而是整層依行序
> 而非座標。詳見 [[sp1b-ocr-geometry-findings]]。第 2 點（假硬錯）的教訓仍然成立，
> 而且是新實作保留型別把關的理由。


1. **抽取錯位**：工程名稱抽到學校名、契約編號抽到金額、學校抽到「提報單位」這個**標籤**。
   合法文件因此永遠歸不了檔，且是「硬湊錯值」而非留空。
   計劃的測試 fixture 是合成的乾淨行（`'工程名稱 114年南陽國小…'`），真實 OCR 輸出從不長那樣。
2. **假硬錯**：OCR 把 `-`(U+002D) 讀成 **`一`(U+4E00，CJK 數字一)**，同一個工程名稱被判不符，
   而當時 UI 只開放編輯 2/9 欄，承辦人無法補救——spec §5.1 寫的是「逐欄確認**或修正**」，計劃只做了「確認」。

**正規化的順序有陷阱**：`一`→`-` 與 `[—–]`→`-` 這兩條**必須排在去空白之後**。
真實值是 `114 一 116`（有空白），排在前面則邊界判斷永遠不成立、規則等於沒作用。

## 已知限制（合併時明確接受）

- `大勇廁所開工報告及相關文件.pdf`：第 1 頁 OCR 零標籤命中、唯一訊號是退路句，與必須放行的正常樣本同型，
  純文字無法區分。放行但除開工日外全 null（不硬湊，符合 spec §5.4-3 精神）。
- `工期I`／`開工I` 與比對表是**單向同步**：表內改會同步到上面，反過來不會；送出以上面為準。
- **OCR 全失敗無手動退路**（spec §7 有此條但未實作）：兩解析度都掛掉就 500，該份 PDF 歸不了檔。
- `missingDateFamily` 守門規則僅 1 份真實樣本佐證（n=1），泛化性未驗證。
- `SCHOOL_NAME_MARKERS` 只含國小/國中/小學/中學，高中/專科會誤殺成 null（不擋歸檔）。
