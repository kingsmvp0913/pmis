2026-08-08 使用者指定「需要影像辨識的 PDF 是最麻煩的部分,要優先解」。做完基礎建設
並**量化之後決定:明細不走 OCR,只用它做涵蓋範圍偵測**。要再碰這塊之前先讀完這篇,
不要重跑這些量測(每次都要幾十秒到幾分鐘)。

## 已經建好、可以直接用的東西

- `ocr/ocr-driver.ps1` 除了行框,也輸出 **word 級的框**(`words[]`:t/line/x/y/w/h)
  與頁面尺寸(`pw`/`ph`,DIP)、**點陣圖真實像素尺寸**(`bw`/`bh`)。
- `filetypes/pdf.js` 的 `extractItemsOcr(file, {ocr, width})` 把它換算成與
  `extractItems` **同一種形狀**的 items(PDF 點、y 由下往上)。座標型讀取器理論上
  能原封不動吃掃描件。
- `daily-log-scan.js` 的 `scanCoverage()`:回報一份掃描件涵蓋哪些日期。
- 測試 `tests/ocr-items.test.js` 用**注入的假 OCR 輸出**驗換算,不依賴機器語言包。

## 三個換算細節(做錯就整份對不上,已寫成測試)

1. **比例尺要用 `decoder.PixelWidth`,不是 `DestinationWidth`**。這台機器顯示縮放
   125%,要求 2200 實際給 2750,用要求值換算所有 x 偏移到 1.247 倍(實測)。
2. **y 用「整行字框底的中位數」**。同一行裡「一」的框高 7px、「誌」60px,
   逐字換算會把一列拆成兩三列。OCR 本來就分好行了,用它的分組最穩。
3. **相鄰字要併成詞,門檻用整行字高的中位數**。用單字字高會把「第/一聯」拆開
   (「一」只有一橫),讀取器的 `find(/^第一聯$/)` 就永遠找不到。

修補層只做兩件可稽核的事:小數點被讀成中點(`0·65`→`0.65`,只在整個 token 就是數字時)、
表頭標籤吸附回固定字彙(至少七成字元相同才吸)。**刻意保守**——寧可留錯字讓完整性
關卡看得見。

## 量測結果(饒平 `0711A-0711A.pdf`,同一份檔的文字層當答案卷)

| 解析度 | 數字格正確 | 讀不到→null | **讀成別的數字** |
|---|---|---|---|
| 1600 | 38.9% | 61.1% | 0.0% |
| **2200** | **51.5%** | 47.9% | **0.6%** |
| 2800 | 45.5% | 52.7% | 1.8% |
| 3400 | 43.7% | 51.5% | 4.8% |
| 5000 | 12.6% | 78.4% | 9.0% |
| 2200+3400 取共識 | 42.5% | 56.9% | 0.6% |

- **最佳解析度是 2200**(≈332dpi),再高反而更差,而且讀錯的比例暴增。
- 表頭那一行:鎮西 60 頁實測**填報日期 100% 正確、0 讀錯**;天氣/工程名稱/工期/
  進度同一行也都對。字大、獨立、沒有格線干擾。
- 真實掃描件(忠信 22MB)的表頭一樣乾淨;**出工那個小數字網格會糊成
  `0000000`、`0000001`**——一整排 0 被連成一個 token。

## 為什麼不接成讀取器的後備(結論,別再重來)

「少一格」看得見(完整性關卡會報 A6/A7),「多一個錯的數字」看不見:
值本身自洽、累計也自洽,SP3 39 條沒有一條攔得住,一路寫進每日施工紀錄 → 監造報表
→ 估驗計價。實測 21→20、2590.00→09 就是這種。**0.6% 的靜默污染率,配上只有一半的
回收率,期望效益是負的。**

要真的把明細做起來,唯一有機會的方向是**按格子切圖再 OCR**
(`PdfPageRenderOptions.SourceRect` 可以只算某個矩形),把密集網格變成單格辨識;
成本是每頁數十次 OCR 呼叫。沒做,因為那要先有「表格線偵測」才知道格子在哪。

## 已交付的用途

`scanCoverage()` 把「這份讀不到」變成「這份涵蓋哪 N 天」。實測 **11301 忠信**
(整案沒有任何可讀日誌):`0216-0229掃描.pdf` → 2/16~2/29 共 14 天、
`忠信…3.1-3.18.pdf` → 3/1~3/18 共 18 天,兩份都完整無缺口。
也能用來判斷掃描件是不是與已讀得到的檔重複(宜謙 31 份裡有 14 份就是重複的)。
