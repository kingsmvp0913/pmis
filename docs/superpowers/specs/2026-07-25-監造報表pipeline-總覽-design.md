# 監造報表 Pipeline — 總覽設計(藍圖)

> 本文是「施工日誌 → 監造報表」端到端 pipeline 的總覽藍圖。各子專案(SP0–SP4、SP-P)之後各自有細部 spec 與 implementation plan;本文定調整體職責切分、資料流、跨切面決策與建置順序,任何一 SP 開工都對得回本文。
>
> **狀態**:草案,待使用者 review。日期 2026-07-25。

## 1. 目標與背景

把「由廠商提供的施工日誌等文件,自動彙整成公共工程監造報表 `.xlsm`」這件事,從現行「上傳施工日誌→從零手刻附表五」的做法,改為**符合實際承辦流程的多步驟、可驗證 pipeline**:以使用者提供的監造報表 `.xlsm` 範本為填寫目標,分階段由不同來源文件填入,並在關鍵關卡做一致性驗證。

正式使用環境**不安裝 AI**;所有 AI 只用在開發期(產固化讀取器、寫程式)。

## 2. 關鍵發現:範本是「自算活頁簿」

監造報表 `.xlsm`(桌面實例約 700KB,**含 VBA 巨集**)共 7 個分頁,**只有 3 個區塊需要填原始值**,其餘全由 Excel 公式自動帶出:

| 需填的輸入區 | 來源 | 自動帶出 |
|---|---|---|
| **工程基本資料** B1:B8,B10(9 值:工程名稱/監造單位/主辦機關/設計單位/承包廠商/契約金額/契約工期/開工日期/工程編號) | 開工報告表(經決標公告審核) | 封面、封面(2)、監造報表 全靠 `INDEX/MATCH 工程基本資料` 帶出;B9 完工期限 =`B8+B7-1` |
| **契約詳細價目表** A:E(項次/項目/單位/數量/單價) | 發包經費總表 | F 複價 =`ROUND(E*D,0)`;每日施工紀錄 A~F 列 =`INDEX(契約詳細價目表…)`;監造報表項目同步 |
| **每日施工紀錄** 日期欄塊(J,K,L… 每天一欄 × 各項次列)填「本日完成數量」 | 施工日誌 | 累計數量 G=`SUM(日欄)`、累計金額 H=`G×單價`、完成% I=`H/複價` 全自動 |

**推論**:產出監造報表 = 把值注入這 3 區、讓範本公式自算;不是從零建表。

## 3. 實際承辦流程(6 步)

1. 取得**決標公告**(公文,固定格式)。
2. 用決標公告**審核開工報告表**(廠商提供,格式因廠商而異);不一致 → 請廠商重產。
3. 用開工報告表內容填**工程基本資料**分頁(Excel 自動產封面/封面(2)/監造報表)。
4. 用**發包經費總表**(內部固定格式)填**契約詳細價目表**分頁;**項目變多時,監造報表 / 每日施工紀錄的 `INDEX` 公式列要同步擴增**。
5. 上傳**施工日誌** → 經 48 條驗證 → 過關後補**每日施工紀錄**分頁(逐日 per-item 本日完成數量)。
6. 監造報表寫好 → 廠商發**公文**(固定格式) → 依其日期/文號產**我方公文**;我方發文日期須 ≥ 廠商公文日期;廠商來不及給時可先手動輸入文號+日期。

## 4. 子專案切分

### 跨切面基座(先於功能子專案)

**SP0 — 範本填寫引擎**
- 職責:給一份 `.xlsm` 範本 + 一組寫入操作 → **保留巨集/公式/格式**地寫入、重算、另存。純基礎設施,不懂業務。
- 技術:Excel COM(見 §5)。對外 `fillTemplate(templatePath, outPath, operations)`;operations 為低階通用指令:`setCell` / `setRange` / `copyRowDown`(把公式列往下複製 N 列,Excel 自動調相對參照,供步驟 4 項目擴列)。
- 狀態:COM 可行性 spike 已實證(清值保公式、保巨集、合併格處理皆通)。

**SP-P — 廠商讀取器一般化 + onboarding**
- 職責:把現行「單一施工日誌讀取器」一般化,並簡化安裝為零操作。
- registry:`vendorKey → 一支` 改為 `vendorKey → { 施工日誌, 開工報告表 }`(廠商 × docType)。
- `gen-vendor-parser` skill:加 `docType` 參數;產生時**廠商名先自動掃樣本「承包廠商」欄,掃不到才問**;產線不接 AI(產出純程式 `.pmisparser.js`),commit 進 repo。
- onboarding:正式環境**啟動時自動 `git pull` + 掃描讀取器檔 → 有廠商就更新、沒有就新增廠商並綁定**(連按鈕都不用);現行 bulk 上傳 / install-bundled 手動 UI 退役。
- 為 SP3(施工日誌讀取器)的前提。

> **更正(2026-08-01)**:原訂「開工報告表也走固化讀取器」已推翻——清點 25 份開工報告表樣本,**24 份是掃描蓋章件、可抽文字量為 0**,正式環境又不裝 AI/OCR。SP1 改為「決標公告自動解析 + 開工報告表人工對照」,不再需要 docType 一般化(仍延後,待未來真有第二種 docType 再做)。詳見 [`2026-08-01-SP1-工程基本資料-design.md`](2026-08-01-SP1-工程基本資料-design.md) §2。

### 功能子專案(依序)

| SP | 內容 | 輸入 | 輸出 | 依賴 |
|---|---|---|---|---|
| **SP1** | 決標公告解析 → 與主檔比對審核 → 填工程基本資料 | 決標公告(自動)、開工報告表(人工對照) | 工程基本資料 9 值寫入 .xlsm;差異清單 | SP0 |
| **SP2** | 發包經費總表 → 契約詳細價目表 + 同步擴列 | 發包經費總表 | 契約詳細價目表寫入;監造報表/每日施工紀錄公式列擴增 | SP0 |
| **SP3** | 施工日誌 48 條驗證 → 填每日施工紀錄 | 施工日誌 | 硬錯清單(阻擋)/軟警告;通過則寫入逐日本日完成數量 | SP0、SP2、SP-P |
| **SP4** | 依廠商公文產我方公文 | 廠商公文(或手動文號+日期) | 我方公文,發文日期 ≥ 廠商日期 | SP3 |

**建置順序**:SP0 → SP-P → SP1 → SP2 → SP3 → SP4(SP0/SP-P 為基座;SP3 的 E 類驗證需 SP2 的契約基準)。

> **更正(2026-08-01)**:SP1 的細部 spec 另有兩處推翻本文——① 上表 SP1 的依賴由「SP0、SP-P」改為「SP0」(開工報告表不再走讀取器);② **契約工期無法由決標公告推導**,27 組樣本驗證僅 14 組相符,改由開工報告表人工輸入,故決標公告自動解析為 5 值而非 6 值。見 SP1 spec §4.3。

## 5. 跨切面技術決策

- **寫 .xlsm 走 Excel COM**,且 **COM driver 必用 Windows PowerShell 5.1**(pwsh 7 以 .ps1 跑 COM 物件走訪間歇回 null);驅動腳本含中文須 **UTF-8 with BOM**;合併格 `UnMerge→Clear→Merge`;清值保公式用 `SpecialCells(constants)`;存檔 FileFormat=52 保巨集;跑前殺殘留 `EXCEL.EXE`。細節見 memory `xlsm-excel-com-findings`。
- **金額一律台灣四捨五入 `ROUND_HALF_UP`**,非 Excel 銀行家捨入;沿用現有 `report.js` 的 `roundHalfUp`。
- **驗證嚴重度**:硬錯誤=阻擋產出且列出所有錯誤位置(哪天/哪項次/哪欄);軟警告=標示但可產。使用者確認**不給強制產出**。
- **累計完成金額**:施工日誌 dailyRows 只有累計完成*數量*;驗證/填寫層自行逐日累加「本日完成金額」推導累計金額,並以 `header.本日累計金額` 當日層級權威值交叉核對。
- **現有 `report.js`(從零手刻附表五)基本被範本填寫路線取代**(Rule 7 衝突已攤開);頂多保留 `roundHalfUp` 工具。舊「上傳施工日誌→自動產表」端點(history-routes)行為改由 SP3 的驗證關卡接手。

## 6. 資料與檔案

- **範例庫**:`docs/samples/`(依輸入類型分夾;公版範本 + 驗證清單版控,其餘大二進位 gitignore)。
- **公版範本**:`docs/samples/監造報表範本/監造報表_空白公版範本.xlsm`(由實例清成,巨集/公式保留、輸入區清空;待客戶確認夠不夠乾淨)。
- **契約詳細價目表**不另存 DB,權威基準即 .xlsm 內該分頁(由 SP2 建);SP3 的 E 類驗證直接對它。
- 需要的 DB 異動(細節留各 SP spec):讀取器 registry 的 docType 維度;公文紀錄(SP4)。

## 7. 待辦 / 暫緩

- **發包經費總表範例**:使用者稍後提供(固定格式)→ SP2 開工前補。
- **驗證清單備註待定案**(SP3 spec 處理):E3 項目名稱一致是否升為硬錯誤、C1 標示首個錯誤日、F4「期末」定義、J2/J3 與單位一致是否重複。
- **公版範本客戶確認**:確認 `監造報表_空白公版範本.xlsm` 夠乾淨後才定為正式底稿。

## 8. 測試哲學

- SP0:純函式(operations 建構、copyRowDown 列數)單元測 + 需 Excel 的整合測(寫入後讀回斷言值落地、公式重算、巨集仍在)。計畫第一步先做 COM round-trip spike(已完成)。
- SP1–SP4:每條規則/對應以「為何而測」編碼(Rule 9);驗證類檢查各自可單獨測(fixture 施工日誌 → 預期硬錯/軟警告)。

## 9. 不在範圍

- 不改核心 Odoo 檔或 `custom_addons/`(本 pipeline 走 `app/` Node);不做超出各 SP 議定 spec 的欄位/模型/邏輯。
