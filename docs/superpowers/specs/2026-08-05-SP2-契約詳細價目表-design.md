# SP2 — 發包經費總表 → 契約詳細價目表

> 狀態:**已實作**(2026-08-05)。本文為設計依據與實測事實,規則的權威來源。
> 上游:[`2026-07-25-監造報表pipeline-總覽-design.md`](2026-07-25-監造報表pipeline-總覽-design.md) §4。

## 1. 目標

把發包經費總表的施工項目與費用項目,寫進監造報表 `.xlsm` 的「契約詳細價目表」
分頁 A:E 欄,並把「每日施工紀錄」「監造報表」兩分頁引用它的 INDEX 公式列擴增到
足夠容納。F 欄複價由範本公式 `ROUND(E*D,0)` 自算,**不寫死值**。

## 2. 實測事實(31 份樣本,規則的依據)

以下每一條都影響了設計,不是背景說明。

1. **施工項目 + 費用項目的複價和 = 表上「發包工程費合計」**,30 份有明細的樣本
   無一例外;且該合計等於決標公告的契約金額(大美 1,036,370、龍井 3,330,000、
   南陽 3,122,168 皆逐一驗證)。
2. **複價恆等於 `ROUND(數量×單價)`**:1094 列全部符合。故交給範本公式重算不會
   產生差額,而對不上就代表檔案被人改過。
3. **第一張詳細價目表常是沒清乾淨的舊底稿**:南陽、新光、東榮、重興廁所、
   重興汙水這 5 個檔案的第一張表,施工小計**全都是 1,185,308**(南陽的數字)。
   照分頁名稱挑會 100% 挑到錯的那張,而且錯得看起來完全正常。
4. **一個工程可能跨多個檔案**:重興 = 廁所 871,943 + 汙水 812,102 = 1,684,045
   = 決標金額。
5. **分頁命名有 6 種變體**:`詳細價目表` / `詳細預算表` / `詳細表` /
   `(標單)詳細價目表` / 尾端帶空白 / `(2)`。
6. **1 份完全沒有明細**(臺中市大勇紅磚道):只有經費總表與預算總表,兩者都只到
   「壹 直接工程費」大類。這種檔案建不出價目表。
7. **費用項目不限五個**:多數是貳~陸,四湖跳遠有到玖共 8 個。
8. **範本的公式列比想像中少**:每日施工紀錄鋪到第 37 列(36 項)、
   **監造報表只到第 40 列(31 項)**。樣本項目數 11~39,**多數案子都會超過 31,
   擴列是常態不是例外**。

## 3. 決策(2026-08-05 與使用者逐項定案)

| # | 決策 | 理由 |
|---|---|---|
| 1 | 價目表 = 施工項目 **+ 費用項目**,不含大類與小計/合計列 | 唯有如此合計才等於決標金額,可與決標公告互相驗算;大類/小計列收下會讓累計金額重複計算 |
| 2 | 挑表**以決標金額自動比對**,對不上才列候選讓人選 | 見事實 3;分頁名稱不可靠,金額是唯一客觀判準 |
| 3 | 重傳**整張覆蓋**,但覆蓋前顯示逐項差異 | 廠商會改舊項目而不只是加新項目,補充式合併會產生「一部分新、一部分舊」且合計對不上任何一版契約的表 |
| 4 | 項次**照原樣保留**(`1`..`N`、`貳`..`陸`) | 施工日誌讀取器解出來的就是這個形式(`parser-jinda.test.js:56,88`),重編號會讓 SP3 的契約表核對全部對不到 |

**不在範圍:契約變更。** 監造報表分頁本身有「契約變更次數」「原契約/變更後契約
金額」欄位,代表這套表預期契約變更是獨立記錄的;用覆蓋原表去模擬,日後就對不出
原契約。SP2 只處理「同一版契約的價目表建立與修正」。

## 4. 資料流

```
上傳 1~N 份發包經費總表
  → POST /api/projects/:id/contract-items/parse    純唯讀
      每個檔解析所有分頁 → 結構判定取候選 → 以決標金額挑組合
      → { 決標金額, selected|null, candidates, errors, diff }
  → 承辦人確認(或自行勾選候選)
  → POST /api/projects/:id/contract-items/confirm  檔案重送 + picks
      重新解析 → 合計比對 → 卡控 → 寫入 .xlsm → 落庫 → 歸檔來源檔
```

檔案送兩次的理由同 SP1B:parse 落檔的話,卡控沒過時會留下一份沒人確認過的
來源檔與價目表。**confirm 不吃前端送來的項目**,只吃「選了哪幾張分頁」——
信任前端送的項目等於讓任何人繞過卡控直接寫進契約價目表。

## 5. 抽取規則

**分頁判定不看名稱**(事實 5),改用結構特徵:**A 欄為阿拉伯數字且該列有單價的
列數 ≥ 3**。實測分離乾淨——詳細價目表 6~34 項,經費總表恆為 2 項(那 2 項是
「柒 工程管理費」下的學校/縣府管理費)。判定不必完美,**金額比對是最後防線**。

**列分類**(A 欄):

| 樣態 | 處理 |
|---|---|
| 純阿拉伯數字 + 數量/單價/複價齊全 | 施工項目,收錄 |
| 貳參肆伍陸柒捌玖拾 + 數量/單價/複價齊全 | 費用項目,收錄 |
| 壹(無數量單價) | 大類標題,排除 |
| A 或 B 欄含「小計/合計/總計」 | 排除 |

正規化:異體字「参/參」、千分位、尾隨空白(樣本裡 `1,033 ` 是常態)。

## 6. 挑表演算法

搜尋空間限制為「**每個檔案至多取一張**」:同一檔的兩張表是同一份工程的舊版與
新版,相加沒有意義;不設限會生出一堆湊得出數字但荒謬的組合。跨檔案相加則是
真實需求(事實 4)。

唯一命中 → 採用;命中多組或全部落空 → `matched: null` + 完整候選清單,交由
承辦人勾選(系統挑哪一組都可能是錯的)。

## 7. 卡控

| 規則 | 時機 |
|---|---|
| 工程須已填決標金額 | parse/confirm 入口 |
| 檔案須有明細分頁 | parse |
| 合計 = 決標金額 | confirm(手動勾選時擋的就是這條) |
| 項目名稱不得為空 | parse 提示 / confirm 硬擋 |
| 數量、單價須 > 0 | 同上 |
| 複價 = ROUND(數量×單價) | 同上(事實 2) |
| 項次不得重複 | 同上——範本靠 `MATCH(項次)` 拉資料,重複時永遠只回第一筆,第二筆的施工進度會靜默記到第一筆頭上 |

## 8. 寫入

- `契約詳細價目表!A2` 起 `setRange`,五欄(項次/項目/單位/數量/單價)
- **擴列排在寫值之前**:公式列不存在的話,寫進去的項目在那兩個分頁上看不到
- **殘留清除**:新表比舊表短時,多出來的舊列補 null 清空,否則會原封不動留著,
  看起來像契約真的有這些項目
- 常駐檔 `data/reports/project_<id>/監造報表.xlsm`,先寫 tmp 再 `renameSync`
  換掉本尊(COM 中途失敗時原檔完好)。⚠️ `fillTemplate` 與 `renameSync` 之間
  不得插入任何 `await`(同 `project-basics-routes.js:152` 的隱性不變量)
- **報表寫成功才落庫**:順序反過來,COM 失敗時會留下「DB 說有、報表沒有」的價目表
- 來源檔歸檔為 `kind='budget_sheet'`,比照開工報告表只留最新一份

## 9. DB

`contract_items(project_id, seq, item_no, name, unit, quantity, unit_price)`。

**這不是權威來源**——權威是 .xlsm 內該分頁。存在的唯一目的:重傳時依**項目名稱**
比出改了什麼,以及日後 SP3 把已填施工進度搬到新位置。只剩列位置可比對的話,
而列位置正是重傳時會位移的東西。

## 10. 測試

- fixture 一律**從實檔產生**(`scripts/make-budget-fixtures.js`),不手打——
  `docs/samples/` 的 xls/xlsx/xlsm 不版控,而 SP1B 手打過的 fixture 讓規則
  永不觸發卻全綠。7 份 fixture 各代表一種實測樣態(雙表殘留、跨檔合併、
  8 個費用項目、39 項擴列、完全無明細)
- 選表演算法以南陽(挑第二張)、重興(跨檔相加)、大美(單張直取)三個真實
  案例各釘一支
- 寫入層在路由測試中 mock,真正的 Excel COM 由 SP0 的整合測涵蓋
