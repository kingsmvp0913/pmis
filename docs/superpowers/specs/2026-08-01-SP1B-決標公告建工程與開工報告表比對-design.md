> 上位藍圖見 [`2026-07-25-監造報表pipeline-總覽-design.md`](2026-07-25-監造報表pipeline-總覽-design.md)。

## 1. 目標

兩件事，同一分支，各自可獨立驗收：

- **階段一**：把 SP1 的「工程基本資料」頁折進「新增工程」，改由**上傳決標公告驅動建立工程**；
  承包廠商／主辦機關在主檔中不存在時，當場詢問並建檔綁定；決標公告 PDF 歸檔留存、日後可下載。
- **階段二**：每個工程可上傳**開工報告表**，與已歸檔的決標公告逐欄比對，
  產生錯誤清單供承辦人發文請廠商修正。

階段二依賴階段一的歸檔基建（要拿歸檔的決標公告當比對基準），故不可對調順序。

|---|---|
| 決標公告 5 值可自動解析 | **延續**，解析器不動 |
| B2/B4 監造/設計單位存系統設定 | **延續** |
| B7 契約工期、B8 開工日期須人工輸入 | **延續**（階段二的比對不改變這點） |
| 決標公告「只讀不存」 | **推翻**：改為歸檔留存（見 §4.3） |

| 決標公告「履約起迄日期」不解析、不顯示 | **部分推翻**：階段二解析它，當開工/竣工日的比對基準，但只到提示級；仍**不**用它推導契約工期（見 §5.3） |

### 2.1 為何折進工程頁（推翻 SP1 §5.4 的獨立頁）

原設計讓「工程基本資料」當側欄獨立頁，進頁第一件事是從下拉選一個工程。
折進工程頁後，`projectId` 來自 URL，於是：

- SP1 為了下拉可改選而加的防呆（commit `07b7675`：凍結 projectId、改選即作廢裁決結果）
  **不再需要**——問題本身消失，不是被刪掉。但「送出時用的 id 必須與畫面顯示的一致」
  這條不變量仍須在測試中保留。
- 新增模式下**逐欄裁決是多餘的**：裁決比對的是「決標公告值 vs 主檔既有值」，
  全新工程主檔為空，無可衝突，直接採用公告值。裁決只在編輯模式且主檔已有值時才有意義。

沿用既有慣例：`projects.js:67` 的 `renderEdit()` 已是 `isNew = id === 'new'` 的新增／編輯共用形態，
`vendors.js:172` 已有 `if (!isNew)` 才顯示某區塊的先例。不新增 route。

### 3.3 值的格式變異（真正的坑）

1. **契約金額有國字大寫**：`貳佰肆拾伍萬陸仟元整`（台西）、
   `新台幣:貳佰捌拾壹萬肆仟叁拾貳元整`（鹿場）。決標公告一律阿拉伯數字
   → **必須寫國字大寫轉數值**才能比對。
2. **工期有兩種基準**：多數為 `150 日曆天`，但**明禮是 `160 工作天`**。
   由開工日→竣工日推導出的是日曆天，工作天案例必然對不上（見 §5.4）。
3. **工期埋在句子裡**：大美是 `機關通知日起 90 日曆天竣工`。
4. **工程地點有兩種寫法**：街道地址（`雲林縣北港鎮光明路59號`、
   `638 雲林縣麥寮鄉橋頭村仁德路248號`，有的帶郵遞區號）或直接寫校名
   （`雲林縣台西國中`、`雲林縣斗南鎮石龜國小校內`）。
5. **臺／台異體字混用**：同一份文件內即混用——`雲林縣台西國中` vs `雲林縣立臺西國民中學`；
   臺中市案兩種寫法都出現。**不正規化會製造純粹的假警報。**

### 3.4 開工報告表為掃描件，OCR 只能預填

24 份中絕大多數為掃描蓋章件。已實測 Windows 內建 OCR（技術細節詳見 memory
`kickoff-report-ocr-findings`）：零安裝成本、繁中 `zh-Hant-TW` 可用、2.5–5 秒／2 頁。

**逐欄辨識率**（以決標公告的權威值為真值，24 份全量比對）：

| 欄位 | 2200px | 3400px | **聯集 2200+3400** |
|---|---|---|---|
| 主辦機關 | 21/24 88% | 21/24 88% | **21/24 88%** |
| 工程名稱 | 18/24 75% | 19/24 79% | **20/24 83%** |
| 契約編號 | 17/24 71% | 18/24 75% | **19/24 79%** |
| 契約金額 | 16/24 67% | 16/24 67% | **17/24 71%** |
| 決標日 | 14/24 58% | 15/24 63% | **15/24 63%** |
| 合計 | 86/120 72% | 89/120 74% | **92/120 77%** |

另單獨量測**契約工期**（真值取自 SP1 §4.3 的 13 組）：**6/13 = 46%**，全欄最低。
失敗樣態：南陽 `150`→`_J50_`、石龜 `120`→`__J_?O_`、豐榮 `160`→`一』一一`；
橋頭／僑美／大勇完全讀不到（推測為**手寫**填入）。

**三個必要但書**：
1. 此為**下限**。未命中可能是 OCR 錯，也可能是兩份文件本身確實不同——
   而後者正是本功能要偵測的。不逐份人工核對無法分離。
2. **契約金額被低估**：台西、鹿場等份用國字大寫，與決標公告的阿拉伯數字永遠字串不相等，
   被計為未命中，但非 OCR 讀錯。實作國字轉數值後此欄會上升。
3. 工程地點、契約規定開工日／竣工日**未量測**——決標公告側無可當真值的對應欄位。

### 3.5 提升辨識率的手段（已實測）

**多解析度聯集**：以 2200px 與 3400px 各跑一次、取聯集，72% → **77%**。
加入第三個解析度（1500px）**增益為 0**，成本卻多 50%，故**只跑兩個**。
改善非單調（四湖跳遠場在 3400px 多讀出 4 欄，東榮國中反而少 2 欄），
顯示每份文件的最佳解析度不同——這正是取聯集有效的原因。
聯集在預填情境下是正當的（承辦人本就要逐欄確認）；若用於裁決則不正當，會虛增信心。

**標籤變體**（§3.2）成本近乎零，應納入，但**不要期待它提升辨識率**——
24 份中僅元長廁所一份使用變體。它是補完整性，不是提辨識率。

**打不破的天花板：手寫。** 橋頭、僑美、大勇的工期欄無論解析度或標籤如何調整都讀不到。
這幾份必須人工輸入，屬 Windows OCR 的硬限制。

### 3.6 故 OCR 只作預填，不作裁決

讀得到就填入、讀不到留空，**最終值一律以承辦人逐欄確認後的為準**。

77% 表示承辦人平均每 8 欄有約 5 欄按確認即可、3 欄需修正——比從零輸入 8 欄省事得多，
故預填值得做。但同一個 77% 也徹底排除讓 OCR 裁決：若直接以 OCR 結果判定「與決標公告不符」，
每三欄就會出現一個假警報（南陽案會因 `_J50_` 要求廠商修正一份實際正確的文件）。
**假警報比沒警報更傷**——幾次之後承辦人會學會直接忽略警告，功能等同白做。

## 4. 階段一：決標公告產生工程

### 4.1 前端

改造 `app/public/js/views/projects.js` 的 `renderEdit()`，不新增 route。

```
#/projects/new     新增模式：決標公告上傳區 + 預填表單 + 廠商/學校裁決
#/projects/<id>    編輯模式：同上，另加「監造報表基本資料」區塊
                   （契約工期、開工日期、監造/設計單位、寫入報表鈕）
```

側欄 `app.js:92` 的 `{ hash: '#/basics', label: '📄 工程基本資料' }` 移除；
`#/basics` route 一併退役（其功能已折入工程頁）。

**寫監造報表 `.xlsm` 必須是獨立按鈕**，不得隨「儲存」連帶觸發——
它要開 Excel COM、可能重試失敗，改個保險到期日不該去開一次 Excel。

決標公告上傳可略過，直接手動填（沿用既有表單）。

### 4.2 廠商／學校比對與建檔

**逐字比對，不做模糊比對。** 名稱正規化只做 trim 與全形空白轉半形。
未命中即顯示「找不到『○○』」＋建立鈕，由承辦人決定。

理由：模糊比對綁錯廠商，錯誤會一路污染監造報表與後續所有 SP；多按一次按鈕的成本極低。
實測佐證：`vendors` 現有的「晉林土木包工業」（由 `parser-onboarding` 從施工日誌建立）
與決標公告解析出的名稱**逐字吻合**。

**學校命名慣例（本 SP 定案）**：`schools.name` 存**機關全名**
（`雲林縣北港鎮南陽國民小學`），`county` 從名稱開頭比對 `schools.js:5` 既有的
22 個縣市常數自動抽取，抽不到則由承辦人從下拉選。

此慣例是硬約束而非偏好：`compareBasics` 直接拿 `schools.name` 當監造報表的 B3 主辦機關
（`project-basics-routes.js:92`），存簡稱會導致每次比對都判定不一致。
目前 `schools` 僅有 1 筆測試資料，現在定慣例的成本為零。

`vendor_id` / `school_id` 綁定只在**新建工程時**發生；既有工程的改綁仍屬廠商／學校管理功能，
不在本 SP 範圍（沿用 SP1 §5.3 的決定）。

### 4.3 歸檔

新增 `project_attachments` 表。**不擴充 `submission_history`**——那張表的語意是
「每月／督導繳交週期」，綁著 `period`/`deadline`/繳交狀態邏輯（`history-routes.js:65-99`），
塞入工程層一次性文件會污染繳交狀態計算。

```sql
CREATE TABLE IF NOT EXISTS project_attachments (
  id            SERIAL PRIMARY KEY,
  project_id    INTEGER NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  kind          TEXT NOT NULL,                  -- 'award_notice' | 'kickoff_report'
  file_path     TEXT NOT NULL,                  -- 相對 DATA_DIR 的 POSIX 路徑
  original_name TEXT,                           -- 下載檔名才不會帶 timestamp 前綴
  uploaded_by   INTEGER REFERENCES users(id),
  uploaded_at   TIMESTAMPTZ DEFAULT NOW()
)
```

**路徑**：`data/uploads/proj_<id>/<Date.now()>_<sanitized原檔名>`。

沿用既有慣例，不另立第四個 `data/` 子根：`uploads/` = 使用者原檔、`output/` = 系統產出、
`reports/` = 常駐 workbook。決標公告與開工報告表都是使用者原檔，
與施工日誌同目錄，靠 `kind` 欄區分。

直接沿用 `history-routes.js` 已 export 的 `safeResolve()`（`:376`，防路徑逃逸，
已有測試 `history.test.js:217-229`）與 diskStorage 設定形態（`:102-118`，
含 `/^\d+$/` id 檢查與 latin1→utf8 中文檔名還原）。`relToData()`（`:121-123`）需一併 export。

> 既有不一致：`uploads`/`output` 用 `proj_<id>`，`reports` 用 `project_<id>`。
> 新功能跟 `proj_<id>`（uploads 家族的慣例）。

**路由**（新檔 `app/server/project-attachments-routes.js`，於 `index.js` 註冊）：

| 端點 | 行為 |
|---|---|
| `GET /api/projects/:id/attachments` | 清單 |
| `GET /api/attachments/:id/download` | `safeResolve` + `res.download(abs, original_name \|\| basename)` |
| `DELETE /api/attachments/:id` | 先 unlink 再刪列 |

### 4.4 建檔與落檔的順序

必須先有 project id 才能決定落檔目錄，故 `POST /api/projects` 改為同時接受 multipart：
先 INSERT project，再落檔，再 INSERT attachment。

**落檔失敗不 rollback 工程**：回 201 並帶 warning，附件可後補。
工程本身已建立成功，砍掉反而製造更差的狀態。

既有 JSON 請求路徑必須維持相容（既有測試 `project.test.js` 全走 JSON）。

### 4.5 必填與硬擋規則

**一律由後端硬擋**，前端驗證只是即時提示，不得作為唯一防線
（沿用 SP1 `project-basics-routes.js` 的既有形態：一次列全、`fields` 陣列回傳給前端指出欄位）。

**建立工程**——依「本次請求是否含決標公告」分岔，避免用單一嚴格門檻擋住補登：

| 路徑 | 必填 |
|---|---|
| **含決標公告** | 工程名稱、工程編號、契約金額、主辦機關、承包廠商（共 5 欄，即解析出的 5 值） |
| **手動新增（無決標公告）** | 工程名稱（維持既有規則，`project-routes.js:110`） |

走決標公告路徑時，**主辦機關與承包廠商必須已完成綁定**——
停在「找不到『○○』」狀態即視同未填，不得送出。
解析失敗而留空的欄位，承辦人須手動補齊後才能送出（不接受空值直接建檔）。

契約工期與開工日期**不列必填**：決標之後、拿到開工報告表之前就要能先建工程。

**寫入監造報表**——維持 SP1 規則：9 值全填才放行，缺任一欄 400 且一次列全
（`REQUIRED = Object.keys(CELL_OF)`）。與「儲存工程」是兩顆獨立按鈕，各有各的必填集合。

**送出開工報告表比對**——8 個比對欄位全部確認完才能送出；
OCR 讀不到而留空的欄位視同未填，一次列全。

空白字串、純空白、陣列值一律視同未填（沿用 SP1 commit `52444b1` 的結論）。

## 5. 階段二：開工報告表比對

### 5.1 流程

```
工程頁 → 上傳開工報告表
  → OCR 預填候選值（讀不到留空）
  → 畫面並排：開工報告表值 / 決標公告值（取自歸檔的那份）
  → 承辦人逐欄確認或修正
  → 比對 → 硬錯清單 + 提示清單
      ├ 有硬錯 → 不得標記為「已核對」，列出全部不符欄位供發文用
      └ 無硬錯 → 標記已核對、歸檔（kind='kickoff_report'）
```

### 5.2 比對欄位與嚴重度

下表除「契約工期」外，比對基準皆為決標公告。
**契約工期是開工報告表的內部自洽性檢查**（表上明載的工期 vs 表上日期推導的工期），
不與決標公告比——理由見 §5.3。

| 欄位 | 開工報告表來源 | 比對基準 | 比對方式 | 級別 |
|---|---|---|---|---|
| 工程名稱 | `工程名稱` | `標案名稱` | 逐字（正規化空白） | 硬錯 |
| 契約編號 | `契約編號` | `標案案號` | 逐字，**不做數值正規化** | 硬錯 |
| 契約金額 | `契約金額` | `總決標金額` | 轉數值後比（含國字大寫） | 硬錯 |
| 決標日 | `決標日期` | `決標日期` | 民國日期正規化後比 | 硬錯 |
| 契約工期 | `契約規定工期` | **開工報告表自身**的 `契約規定竣工日` − `契約規定開工日` + 1 | 天數比 | 硬錯 |
| 學校 | 署名欄 `主辦機關` | `機關名稱` | 逐字（含臺／台正規化） | 硬錯 |
| 縣市 | `工程地點` 開頭縣市 | `履約地點` 去括號註記 | 逐字（含臺／台正規化） | 硬錯 |
| 契約規定開工日 | `契約規定開工日` | `履約起迄日期` 起日 | 顯示差幾天 | 提示 |
| 契約規定竣工日 | `契約規定竣工日` | `履約起迄日期` 迄日 | 顯示差幾天 | 提示 |

**契約編號不得做數值正規化**：格式各機關自訂（`1150113` / `A1150608` / `ywjh11504` / `114-17`），
數值化會把 `0123` 誤判等於 `123`（沿用 SP1 commit `edca759` 的結論）。

**學校用署名欄而非工程地點**：實測 21/24 份的主辦機關署名欄有完整校名，
且與決標公告 `機關名稱` 格式完全一致。工程地點欄則有街道／校名兩種寫法，只能抽縣市。

### 5.3 為何開工日／竣工日只能是提示級

決標公告的 `履約起迄日期` 明載「(預估)」。實測三例：

| 案 | 決標公告履約起迄 | 開工報告表 | 差異 |
|---|---|---|---|
| 南陽 | 115/03/18 – 115/08/14 | 115/03/18 – 115/08/14 | 完全吻合 |
| 古坑 | 115/07/05 – 115/12/31 | 115/07/15 – 116/01/10 | **整體平移 10 天** |
| 豐榮 | 115/07/11 – 115/12/20（163 天） | 真值 160 天 | 天數即不同 |
| 鹿場 | **無此欄** | — | 缺 |

古坑一例關鍵：兩邊算出的工期**都是 180 天**，只是起點差 10 天——
因機關實際通知開工較晚，屬正常，不是廠商填錯。
若將日期列為硬錯，將製造大量假警報。

同時**仍不以履約起迄推導契約工期**（SP1 §4.3 已用 27 組全量驗證推翻：僅 14 組相符）。
本 SP 的工期比對，基準是**開工報告表自身的開工日→竣工日推導值**，
與表上明載的「契約規定工期」互相對照。

### 5.4 三個必須特別處理的例外

1. **工作天 vs 日曆天**：偵測到「工作天」即**不推導、只取表上數字**，並在畫面標明基準。
   由開工日→竣工日算出的是日曆天，工作天案例必然對不上。
2. **國字大寫金額**：需一支國字轉數值純函式（`貳佰肆拾伍萬陸仟元整` → `2456000`）。
3. **非開工報告表的文件**（3/24）：明確報「無法辨識為開工報告表」，不得硬湊欄位。

### 5.5 臺／台正規化

所有涉及名稱與地名的比對，比對前一律將 `臺` 正規化為 `台`（或反之，擇一固定）。
此規則同時套用於學校、縣市兩欄。

## 6. 架構

沿用 SP1 的三層分工，上層不得反向依賴下層的業務知識。

| 層 | 檔案 | 職責 |
|---|---|---|
| OCR | `app/server/ocr/` + PS 5.1 driver | PDF→圖→文字＋座標。**每頁跑 2200px 與 3400px 兩次**（見 §3.5）。不懂業務 |
| 開工報告表 | `app/server/kickoff-report.js` | 從 OCR 輸出抽 8 欄。懂開工報告表，不懂 PMIS |
| 比對 | `app/server/kickoff-compare.js` | 純函式：兩份值 → 硬錯／提示清單 |
| 附件 | `app/server/project-attachments-routes.js` | 上傳／清單／下載／刪除 |

OCR driver 比照 `excel-com-driver.ps1` 的既有形態：**必須用 Windows PowerShell 5.1**
（PS 7 載不動 WinRT 型別）。`PdfPage` 用 `Dispose()` 而非 `Close()`。
WinRT async 需自建 `Await` helper（反射取 `AsTask` 的 generic／action 兩種多載）。

## 7. 錯誤處理

| 情境 | 行為 |
|---|---|
| 決標公告為掃描件 | 沿用既有 `SCANNED_PDF` 訊息，提示改用手動新增 |
| 決標公告單一錨點抓不到 | 該欄留空標「未能解析」，不阻擋其餘欄位 |
| 廠商／學校未裁決就送出 | 400 硬擋，**一次列全**（與既有 `/basics` 一致） |
| 附件落檔失敗 | 工程保留，回 201 帶 warning |
| 開工報告表無法辨識 | 明確報錯，不硬湊欄位 |
| 比對有硬錯 | 不得標記已核對，列出**全部**不符欄位 |
| OCR 全失敗 | 退回全手動輸入，不阻擋流程 |

## 8. 測試

全部可在 pg-mem + 純函式測，**不需要 Excel、不在測試中真的跑 OCR**
（OCR 層以固定輸出當 fixture）。

| 測什麼 | 為何而測 |
|---|---|
| 國字大寫轉數值 | 台西／鹿場的金額否則永遠判不符 |
| 民國日期正規化 | 決標日比對的前提 |
| 工期推導含頭尾 | 少一天則全部案子都判不符 |
| 偵測到「工作天」不推導 | 明禮案否則必然假警報 |
| 臺／台正規化 | 同一份文件內即混用，不正規化＝純假警報 |
| 兩解析度取聯集（任一讀到即採用） | 只跑單一解析度會少 5 個百分點；改善非單調 |
| 標籤變體（`契約約定工期`／`開工日期`）可命中 | 元長廁所否則整份抓不到工期與開工日 |
| 敘述句 fallback 可命中開工日 | 標籤抓不到時的唯一退路 |
| 縣市前綴抽取（含郵遞區號、校名兩種形態） | 工程地點有兩種寫法 |
| 廠商／學校逐字比對三態 | 一致／不一致／缺值須分得開 |
| 硬錯一次列全 | 逐條修正會讓承辦人來回發文 |
| 含決標公告時 5 欄必填、缺任一即 400 | 半套工程會讓後續 SP2/SP3 全部落空 |
| 手動新增仍只需工程名稱 | 提高門檻會擋住舊案補登 |
| 廠商／學校未綁定即視同未填 | 停在「找不到」狀態送出會產生無主工程 |
| 空白字串／純空白／陣列視同未填 | 沿用 SP1 `52444b1`，否則假成功 |
| 提示不得阻擋 | 古坑平移 10 天是正常的 |
| 落檔失敗不 rollback 工程 | 砍掉已建成功的工程是更差的狀態 |
| 附件下載路徑逃逸 | 沿用 `safeResolve` 既有測試形態 |
| 送出用的 projectId 與畫面一致 | SP1 commit `07b7675` 的不變量須保留 |
| JSON 建工程仍相容 | 既有 `project.test.js` 全走 JSON |

## 9. 不在範圍

- 不做開工報告表的**固化讀取器**（廠商×docType 的 SP-P 一般化）。本 SP 走 OCR 預填＋人工確認；
  讀取器路線留待日後評估（標籤既已證實統一，走 OCR 座標配對是可行方向）。
- 不改綁既有工程的 `vendor_id` / `school_id`。
- 不碰契約詳細價目表（SP2）、每日施工紀錄（SP3）、公文（SP4）。
- 不做決標公告掃描件的 OCR fallback。
- 不清理 `DELETE /api/projects/:id` 既有的孤兒檔問題（`project-routes.js:146` 只刪列不刪檔）——
  已知缺陷，但屬既有範圍，另案處理。
