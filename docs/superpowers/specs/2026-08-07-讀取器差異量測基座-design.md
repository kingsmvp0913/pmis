# 讀取器差異量測基座（check-against-truth）— 設計

日期：2026-08-07

## 背景與動機

`parser-pipeline-gaps` 記的第二個結構性盲區：**目前的讀取器驗收拿讀取器自己的輸出當基準**。
所以「讀錯但格式合法」的錯誤（名稱切錯、值掛到鄰居列）永遠驗不出來——輸出是合法字串，
只是內容錯了。

使用者桌面的 `%USERPROFILE%\OneDrive\Desktop\PMIS範例\模板\全案範例\` 有 **49 個完整舊案**，
每案都附一份**人工做好的監造報表 `.xlsm`**。那是外部基準，能打破這個盲區。

### 已實測的版面事實（2026-08-07）

- 49/49 案的成品 `.xlsm` 分頁**完全一致**：
  `封面 | 封面 (2) | 監造報表 | 工程基本資料 | 契約詳細價目表 | 監造內容 | 每日施工紀錄`
- 49/49 案的「工程基本資料」分頁 A1..A10 標籤一致，**B1..B10 對得上
  `app/server/project-basics.js` 的 `CELL_OF`**，9 欄填寫率 **49/49 全滿**
- 開工日期存的是 Excel 日期序號（如 `45338`），不是字串

→ 441 格答案可直接抽，不需版面偵測。

## 核心約束：答案卷本身也可能錯

這些成品是人做的。工具**不得預設答案卷是對的**。具體落實：

1. **不輸出「準確率」**。一個百分比會暗示分母是對的，而這個前提不成立。
   改輸出四態：`一致` / `不一致` / `讀取器沒讀到` / `答案卷沒填`。
2. **每筆不一致，兩邊的值都印出來**，不標誰對誰錯。歸因是人的工作。
3. **「已知等價差異」與「實質差異」分開列**。全形半形、`1070000` vs `1,070,000`
   這類是雜訊，混在一起會把真正該看的淹掉。
4. 工具**只產報告**：不改任何程式、不改任何資料、不寫進 `data/`。

## 範圍（第一版）

**決標公告 → 工程基本資料 9 欄。**

選這一層的理由：49/49 案都有決標公告與答案卷、答案卷 100% 填滿，樣本最完整；
且 `readAwardNotice(fileOrBuffer)` 是純函式加薄 IO，離線可直接呼叫。

### 欄位分兩組

**比對組（5 欄）** —— `project-basics.js` 的 `COMPARABLE`：
工程名稱、主辦機關、承包廠商、契約金額、工程編號。

**觀察組（4 欄）** —— 抽出來列，但**標成「不比對，僅供觀察」**：
監造單位、設計單位（來自系統設定，決標公告結構上沒有）、
契約工期、開工日期（`award-notice.js` 註解：「履約起迄日期是**預估值**，
27 組驗證中 13 組與實際契約工期不符」）。

觀察組照樣輸出的理由：49 案的答案卷剛好能驗證「決標公告推不出契約工期」這個假設。
若多數案推得出來，是現有讀取器少抽了；若推不出來，就確認了那個註解。兩種結果都有情報價值。

## 介面

```
node app/scripts/check-against-truth.js [--root <路徑>] [--case <案名關鍵字>] [--json <輸出檔>]
```

- `--root` 預設 `%USERPROFILE%\OneDrive\Desktop\PMIS範例\模板\全案範例`。
  **禁止寫死絕對路徑**：預設值由 `process.env.USERPROFILE` 組出，且可由 `--root`
  或 `PMIS_TRUTH_ROOT` 覆寫。
- `--case` 只跑符合關鍵字的案子（除錯用）。
- `--json` 另存機器可讀的完整結果（預設只印摘要到 stdout）。

## 模組切分

| 檔案 | 職責 |
|---|---|
| `app/scripts/check-against-truth.js` | CLI：走訪案子、挑檔、呼叫下面兩支、印報告 |
| `app/server/truth-key.js` | 從成品 `.xlsm` 抽答案卷（純函式 + 薄 IO），可獨立測試 |

`truth-key.js` 放 `server/` 而非 `scripts/`：它是可測試的資料抽取邏輯，
與 `award-notice.js` / `project-basics.js` 同層；`scripts/` 下的是不接測試的一次性工具。

### `truth-key.js`

```
readTruthKey(xlsmPath) -> { 工程名稱, 監造單位, ..., 工程編號 }
```

- 分頁名寫死 `工程基本資料`。**與 SP2 挑表不同**：`sp2-budget-sheet-findings` 說發包經費
  總表不能看分頁名（第一張常是別案殘留），但那是廠商自己維護的檔；這裡的分頁名是
  公版範本固定的，49/49 實測一致。
- 抽值前先驗 A1..A10 的標籤與預期相符，**不符就 throw**，不猜。
  標籤驗證是這支工具唯一的防線——版面若哪天變了，靜默抽到錯格會讓整份報告是錯的
  卻看起來正常。
- 開工日期用 `parsers/filetypes/xlsx` 的 `excelSerialToISO` 轉回 ISO 字串。

## 挑檔規則

每案目錄遞迴找檔，依檔名關鍵字分類：

- 答案卷：`/監造報表/` 且副檔名 `.xlsm`
- 決標公告：`/決標/` 且副檔名 `.pdf`

同類命中多份時**全部列出並取第一份**，且在報告裡標明「本案有 N 份，取用 X」——
靜默取第一份會讓「取錯檔造成的差異」看起來像讀取器的錯。

## 報告格式

stdout 摘要：

```
=== 49 案 × 5 比對欄 ===
一致          NNN
不一致(實質)   NN
不一致(等價)   NN
讀取器沒讀到   NN
答案卷沒填     NN
決標公告讀取失敗 NN 案

=== 實質差異(逐筆) ===
<案名>  <欄位>
  答案卷 : <值>
  讀取器 : <值>

=== 等價差異(逐筆,僅供確認正規化是否過寬) ===
...

=== 觀察組(不比對) ===
<案名>  契約工期  答案卷=140  決標公告履約起迄推算=??
```

等價判定沿用 `project-basics.js` 的 `normalizeText` / `normalizeAmount`——
**必須共用而非另寫一份**：另寫一份就會與 production 的判定漂移，
報告說「等價」而系統實際判 diff（或反之）。

## 測試

`app/tests/truth-key.test.js`（只測 `truth-key.js`，CLI 不測）：

- 標籤與預期相符 → 抽出 9 欄
- **A 欄標籤被改掉 → throw**（釘住「不猜」；這是整份報告正確性的唯一防線）
- 開工日期序號 → ISO 字串
- 空白儲存格 → `null` 而非空字串（與比對層的「缺值」語意一致）

fixture 用程式產生的小 `.xlsx`（`XLSX.utils.aoa_to_sheet`），不放真實案子的檔案——
真檔含機關與廠商實名，不進 repo。

## 成功判準

1. `node app/scripts/check-against-truth.js` 跑完 49 案不 crash，輸出上述報告
2. `truth-key.test.js` 全綠，且「標籤被改 → throw」那條確實會在標籤改動時紅
3. 報告裡沒有任何「準確率」字樣；每筆差異都同時列出兩邊的值
4. 全跑測試無新增紅燈

## 明確不做

- 不自動修任何讀取器。這一版只量、不改。
- 不碰契約詳細價目表與每日施工紀錄兩層（下一版）。
- 不處理掃描件施工日誌（尚未查證有無文字層）。
