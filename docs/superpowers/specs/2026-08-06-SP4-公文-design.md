# SP4 — 依廠商公文產我方公文

> 狀態:**設計完成,待實作**(2026-08-06)。本文為設計依據與實測事實,規則的權威來源。
> 上游:[`2026-07-25-監造報表pipeline-總覽-design.md`](2026-07-25-監造報表pipeline-總覽-design.md) §4(第 6 步)。

## 1. 目標

監造報表產好、廠商發函之後,產出我方(監造單位)致學校的函,附件為該期施工日誌與
監造報表。產出物是 `.docx`,掛在既有繳交紀錄(`submission_history`)那一列,
把目前一律回 409 的公文下載路徑打通。

## 2. 實測事實(3 份樣本,規則的依據)

樣本:`docs/samples/公文/` 三份 `.doc`,皆為**我方公文**(廠商公文無樣本)。
以 Word COM 抽文字比對,骨架完全一致,變異點如下:

| | doc_a | doc_b | doc_c |
|---|---|---|---|
| 發文單位 | 呂罡銘建築師事務所 | **大墩規劃設計顧問有限公司** | 呂罡銘建築師事務所 |
| 地址 | 中華路一段7號3樓 | **柳川西路二段140巷8號12樓之2** | 中華路一段7號3樓 |
| 電話/傳真/聯絡人/信箱 | 同 | 同 | 同 |
| 文號 | **銘第**4131-5070112號 | **墩字第**4121-5063012號 | **銘第**4201-5063012號 |
| 受文者 | 大勇國小 | 越港國小 | 南陽國小 |
| 期間句構 | 「承攬廠商**115年6月份施工日誌**及檢送」 | 「承攬廠商**施工日誌(115年6月1日至115年6月30日)**及檢送」 | 同 b |
| 份數 | 各乙式**乙**份 | 各乙式**乙**份 | 各乙式**三**份 |
| 依據 | 摯東 **摯勇字第1150701001號** | 玉森 **玉字第1150630001號** | 晉林 **115晉工字第068號** |

由此得到四條硬事實:

1. **兩個發文單位共用同一組電話/傳真/聯絡人/信箱,只有名稱、地址、字別不同**——
   同一間辦公室兩塊招牌。發文資訊必須綁事務所,不能當全域設定。
2. **廠商文號三家三種格式**,連年份位置都不一樣(`115晉工字第068號` 年在最前)。
   自動解析等於重蹈開工報告表的覆轍(格式不固定 → 讀不可靠),**一律人工輸入**。
3. **我方文號的「字別」寫法本身就不一致**(「銘第」vs「墩字第」)。整串人工輸入,
   **不拆欄位**——拆了就是把一個不成立的格式寫死進 schema。
4. **我方發文日期 = 廠商公文日期是常態**(a 都是 7/1;b、c 都是 6/30)。
   總覽要求「我方 ≥ 廠商」,故**相等必須放行**。

我方公文正文只引用廠商的**名稱、日期、文號**三項(「依據晉林土木包工業115年6月30日
115晉工字第068號函辦理」),廠商名稱系統已有 ⇒ **文號+日期即足以產文**,
不需要廠商公文原件。

## 3. 決策(2026-08-06 與使用者逐項定案)

| 項目 | 決策 | 理由 |
|---|---|---|
| 廠商公文 | 不收檔、不解析,只人工輸入文號+日期 | §2 事實 2 |
| 我方文號 | 人工輸入完整字串 | 公文文號綁事務所自己的收發文簿,可能與非本系統的案子共用流水,系統編不出來 |
| 產出格式 | `.docx` + 純 JS 套版 | 正式環境不必裝 Word;與監造報表的 Excel COM 路線分開,不互相拖累 |
| 發文單位資訊 | 擴充 `firms` 主檔 | §2 事實 1 |
| 份數 | 每次產文時填,預設「乙」 | 3 份樣本 2 份是乙份 |
| 期間句構 | **一律用起迄**「施工日誌(115年6月1日至115年6月30日)」 | 見下方「一條被推翻的推論」 |
| 操作入口 | 繳交紀錄列上的「產公文」 | 公文按鈕本來就在那列;公文往往晚於日誌繳交(要等廠商先發函) |
| 重產 | 直接覆蓋 | 一期一份公文,舊的沒有保留價值 |

## 4. 範本

`app/templates/公文_空白範本.docx`(與監造報表範本同處),由 doc_a 挖空而成,
**15 個佔位符**:

```
{{發文單位}} {{發文地址}} {{電話}} {{傳真}} {{聯絡人}} {{電子信箱}}
{{受文者}} {{發文日期}} {{發文字號}}
{{工程名稱}} {{日誌描述}} {{份數}}
{{廠商名稱}} {{廠商公文日期}} {{廠商文號}}
```

**每個佔位符都壓成單一 `<w:r>`**。Word 原本把「呂罡銘/建築師事務所/函」切成三個 run、
日期切成 `11`/`5`/`年`/`7`/`月`/`1`/`日`;佔位符若跨 run,套版時字串比對就抓不到——
這是 docx 套版最常見的失敗原因,在產範本時就解決,套版端因此只需純字串替換。

期間做成 `{{日誌描述}}` 而非 `{{期間}}`:整段(含「施工日誌」四字與括號)當一個佔位符。
樣本存在兩種句構(§8 末),雖已定案只用其中一種,但把整段留給程式端意味著日後要換寫法
不必動範本。

已知限制:header/footer 寫死「第一頁 共一頁」。三份樣本都是單頁,暫不處理。

## 5. 資料流

```
繳交紀錄列「產公文」
  → 彈窗填 5 欄(帶出該列上次填的值)
  → 硬擋:我方發文日期 < 廠商公文日期 → 400,不寫檔
  → 組值(§6)→ 套版(§7)→ 寫檔 → 更新 official_doc_path 與 5 欄
  → 「公文」下載鈕由 409 變 200
```

## 6. 值的組法

| 佔位符 | 來源 |
|---|---|
| 發文單位/地址/電話/傳真/聯絡人/電子信箱 | `firms`,由 `projects.supervisor_firm` 對應(名稱字串) |
| 受文者 | `schools.name`(經 `projects.school_id`) |
| 工程名稱 | `projects.name` |
| 廠商名稱 | `vendors.name`(經 `projects.vendor_id`) |
| 發文日期 / 發文字號 / 廠商公文日期 / 廠商文號 / 份數 | 人工輸入(存 `submission_history`) |
| 日誌描述 | 見下 |

**日期一律轉民國格式**(`115年7月1日`),與樣本一致。

**日誌描述**一律為 `施工日誌(<起>至<迄>)`,起迄取**日曆期間**而非日誌實際首尾:

「該期月份」= `submission_history.period`(既有格式 `YYYY-MM`,見 `history-routes.js` 的 `ymOf`)。

- 起 = `max(該期月份 1 日, projects.start_date)`
- 迄 = `min(該期月份最後一日, projects.actual_completion_date)`(未竣工則為該月最後一日)

取日曆期間而非日誌首尾,是因為廠商本來就不會逐日填(假日無工),用實際首尾會寫出
「6月2日至6月29日」這種與樣本不符的期間。樣本 b/c 寫的正是完整日曆月 6月1日至6月30日。
首月自開工日起、末月至竣工日止是推導(樣本的月份都落在工期中間,無首月/末月案例)。

**該期沒有任何 `daily_records` → 擋下不產**:公文正文寫的是「檢送施工日誌」,
沒有日誌卻發文等於發出一份不實的函。

## 7. 套版引擎

新模組 `app/server/official-doc.js`:

1. jszip 讀 `app/templates/公文_空白範本.docx`
2. 取 `word/document.xml`,15 個佔位符做字串替換(值先做 XML escape:`& < >`)
3. 重新打包成 `.docx`

**`jszip` 須加進 `app/package.json` 的 dependencies**。它目前只是 `exceljs` 的
傳遞依賴——直接 require 會在 exceljs 升級拿掉它時無聲斷掉。實體已在 `node_modules`,
加宣告不會真的下載東西。

產出檔名 `<period>_公文.docx`。樣本檔名用的是文號中段(`4131-5070112_…`),
但文號整串人工輸入,前綴長度各家不同(「銘第」vs「墩字第」),切不可靠,故不沿用。

存放沿用既有 `report_path` 的根目錄與 `safeResolve` 路徑檢查。

### 一條被推翻的推論(留著,免得下次又推一遍)

設計初稿曾定「整月用『N月份』、非整月用起迄」,**這是錯的**。三份樣本涵蓋的
全都是完整的 6 月,句構卻分成兩種;doc_a 與 doc_c 同屬呂罡銘事務所也用了不同寫法,
所以既不是「整月與否」也不是「哪家事務所」的差別。樣本裡唯一對得上的關聯是發文日
(6/30 當月內發文的兩份用起迄,7/1 次月發文的那份用「6月份」),但 1 比 2 的樣本
不足以立規則。定案:**一律起迄**,不猜。

**`DATE` 欄位注意**:pg 把 DATE 解析成伺服器在地午夜的 Date,JSON 序列化成 UTC 會退一天。
前端一律走 `PmisApp.toDateInputValue`,不可用 `String(v).slice(0,10)`。

## 9. 測試

| 測什麼 | 為何(Rule 9) |
|---|---|
| 套版後解 zip 讀回 `document.xml`,15 個值都到位 | 這是產出物的唯一正確性依據 |
| **全文不得殘留 `{{`** | 漏一個佔位符 = 公文上印著 `{{份數}}` 發出去 |
| 值含 `&`/`<` 時 XML 未損毀 | 學校/廠商名稱出現這類字元會讓 docx 開不起來 |
| 期間起迄:一般月、首月(開工日在月中)、末月(竣工日在月中) | 首末月若不裁切,公文會宣稱檢送了不存在的日期區間 |
| 該期無 `daily_records` → 擋下不產 | 公文寫「檢送施工日誌」卻沒有日誌 = 發出不實的函 |
| 我方日期 < 廠商日期 → 400 **且檔案沒被寫出** | 只驗回應碼會漏掉「擋了但檔案已產」 |
| 我方日期 = 廠商日期 → 放行 | §2 事實 4:相等是常態,誤擋等於整套不能用 |
| 端到端:產出後 `/download/official_doc` 由 409 變 200 | SP4 的驗收條件就是這條路徑通 |
