# SP1 — 工程基本資料(決標公告解析 → 審核 → 填 9 值)設計

> 監造報表 pipeline 子專案 SP1 的細部 spec。上位藍圖見
> [`2026-07-25-監造報表pipeline-總覽-design.md`](2026-07-25-監造報表pipeline-總覽-design.md)。
>
> **狀態**:待使用者 review。日期 2026-08-01。

## 1. 目標

把監造報表 `.xlsm` 的 `工程基本資料` 分頁 9 個輸入值填好,並在填之前用**決標公告**做一致性審核。
填完後,範本自身的公式會把封面、封面(2)、監造報表三個分頁全部帶出來(`INDEX/MATCH 工程基本資料`),
故本 SP 只需寫 `B1:B8` 與 `B10`,`B9` 完工期限是範本公式 `=B8+B7-1`,不寫。

## 2. 前提修正:總覽藍圖的 SP1 前提被樣本推翻

總覽 §4 原訂 SP1 走「**開工報告表固化讀取器**」(比照施工日誌,屬 SP-P 的 docType 一般化)。
清點 `docs/samples/開工報告表/` 25 份 PDF 後,此前提不成立:

| 事實 | 數字 |
|---|---|
| 開工報告表 PDF 可抽文字量 = 0(掃描蓋章件) | **24 / 25** |
| 有文字的 PDF | 1(古坑國中小,1457 字) |
| 另有可讀電子檔 `.odt` | 2 |
| 決標公告 PDF 可抽文字 | **28 / 28** |

正式環境不裝 AI/OCR(總覽 §1),故**開工報告表無法自動解析**。
SP1 改採「決標公告自動解析 + 開工報告表人工核對」。已與使用者確認採此路線。

**連帶影響**:SP-P 的「讀取器 docType 一般化(開工報告表)」在 SP1 不再需要,繼續延後。
若未來要求廠商改交 `.odt`/`.docx`,再回頭做。

## 3. 9 值來源(已用實例對照驗證)

以宜梧國中的 `.odt` 開工報告表對照其已填監造報表,8 欄逐字吻合;
再以南陽國小(決標公告 + 已填監造報表)交叉驗證。結論:

| 儲存格 | 欄位 | 權威來源 | 自動? |
|---|---|---|---|
| B1 | 工程名稱 | 決標公告「標案名稱」 | ✅ |
| B2 | 監造單位 | 系統設定(專案可覆寫) | ✅ |
| B3 | 主辦機關 | 決標公告「機關名稱」 | ✅ |
| B4 | 設計單位 | 系統設定(專案可覆寫) | ✅ |
| B5 | 承包廠商 | 決標公告「得標廠商」 | ✅ |
| B6 | 契約金額 | 決標公告「總決標金額」 | ✅ |
| B7 | 契約工期 | **開工報告表(掃描件)** | ❌ 人工 |
| B8 | 開工日期 | **開工報告表(掃描件)** | ❌ 人工 |
| B9 | 完工期限 | 範本公式 `=B8+B7-1` | — 不寫 |
| B10 | 工程編號 | 決標公告「標案案號」 | ✅ |

自動 5 值、人工 2 值、系統設定 2 值。

**B7/B8 為何不能取決標公告**:決標公告只有「履約起迄日期」,且明載為**預估**值。
- **B8 開工日期**:真正開工日是機關通知後起算。宜梧預估 115/06/12、實際開工 115/06/19,差 7 天。
- **B7 契約工期**:契約工期是契約條款上的整數天(90/120/150/160/180 這類),與預估區間無關。
  以 27 組「決標公告 ↔ 已填監造報表」全量驗證「履約起迄含頭尾天數 = B7」這條推導,
  **僅 14 組相符、13 組不符**(見 §4.3)。開工報告表則直接寫明「契約規定工期 N 日曆天」。

兩者一律由承辦人對照開工報告表 PDF 人工輸入。

**B2/B4 為何不來自文件**:兩者都不在決標公告上(決標公告只有「本工程案委託廠商提供技術服務」
指向另一份技術服務決標公告的案號),開工報告表則只有監造單位、沒有設計單位。
兩個樣本此二值皆為同一家,實務上多為貴公司自己,故存系統設定。

**工程編號的三方一致**:決標公告「標案案號」= 開工報告表「契約編號」= 監造報表 B10。
南陽 `1150113`、宜梧 `ywjh11504` 兩例皆成立。

## 4. 決標公告可解析性(spike 實證)

決標公告是政府電子採購網「友善列印」版面,為固定兩欄表。用 pdfjs 的 item 座標分欄:

| x 區間 | 內容 |
|---|---|
| `x < 45` | 區塊名直排字(機/關/資/料、已/公/告/資/料、決/標/品/項) |
| `45 ≤ x < 130` | 標籤欄(巢狀欄位有前導空白,如「 廠商名稱」) |
| `x ≥ 130` | 值欄 |

同一列的 item y 座標有 ±3 誤差(如「決標方式」標籤 y=415、值 y=413),需容差合併。
標籤過長會換行續行(x 仍在標籤欄、該列無值),值取標籤**起始列**的值欄。

對 `docs/samples/決標公告/` 28 份樣本跑錨點探針,結果:

| 欄位 | 命中 |
|---|---|
| 標案案號 / 標案名稱 / 機關名稱 / 得標廠商 / 總決標金額 | **28 / 28** |

本 SP 需要的 5 個錨點全部 28/28,且皆為「標籤與值同列」,不需跨頁配對邏輯。

### 4.1 實測發現的必要規則

**得標廠商不是「投標廠商1」。** 實測 28 份中有 4 份不是第一家:仁德(第 2)、四湖永慶(第 3)、
豐榮(第 2)、鹿場(第 3)。必須掃 `投標廠商N` 群組、取 `是否得標 = 是` 的 `廠商名稱`,
不得取第一個 `廠商名稱`。

### 4.2 標案案號格式差異

`1150113`、`A1150608`、`TKPS-A1150603`、`DRJH-1140923`、`ywjh11504`、`114-17` — 格式各機關自訂,
**不得用 pattern 驗證或推導**,只能照抄。

### 4.3 反證:決標公告推不出契約工期

曾假設 `契約工期 = 履約迄日 − 履約起日 + 1`(宜梧 120、南陽 150 兩例吻合)。
**以 27 組「決標公告 ↔ 已填監造報表 B7」全量驗證後推翻:僅 14 組相符,13 組不符。**

| 形態 | 例 |
|---|---|
| 小差(契約工期是整數天,預估區間不是) | 大美 91 vs 90、大勇鋪面 91 vs 90、明禮 164 vs 160、橋頭 187 vs 180、豐榮 163 vs 160、元長廁所 118 vs 120、元長鋪面 62 vs 60、東榮廁所 153 vs 160 |
| 大差(預估區間與契約工期完全無關) | 東榮丹娜絲 457 vs 60、鹿場 465 vs 160、石龜 193 vs 120、僑美 123 vs 150、東榮國小 127 vs 150 |

另掃過 28 份決標公告全部欄位,**沒有任何欄位記載契約工期**
(唯一命中「工期」二字的是敘述文字「指數調整價金規定 ⇒ 工期很短」)。

**結論**:B7 契約工期只能由開工報告表人工輸入。
**「履約起迄日期」不解析、不顯示**——它有 48% 機率與契約工期不符,當提示只會誤導承辦人。
連帶地,原本為它而需要的「跨頁 label/value 配對」與「民國日期格式容差」邏輯一併不做(YAGNI)。

## 5. 架構

三層,各層只懂自己那件事;上層不得反向依賴下層的業務知識。

### 5.1 解析層(不懂業務)

**`app/server/parsers/filetypes/pdf.js`** — 新增一支匯出,既有 `extractPages()` 不動
(廠商讀取器仍在用,不得破壞)。

```js
extractRows(filePath) -> Promise<Array<{ page: number, rows: Array<{ label, value }> }>>
```

依 §4 的 x 分欄 + y 容差合併,回逐頁的 `{label, value}` 列。不做任何欄位語意判斷。

### 5.2 決標公告層(懂決標公告,不懂 PMIS)

**`app/server/award-notice.js`** — 新檔

```js
parseAwardNotice(pages) -> {
  工程名稱, 主辦機關, 承包廠商, 契約金額, 工程編號   // 5 值,不含契約工期(見 §4.3)
}                                    // 純函式:吃 extractRows 的輸出,不碰檔案系統
readAwardNotice(filePath) -> Promise<同上>   // 薄 IO = extractRows + parseAwardNotice
```

- 錨點對應見 §3;得標廠商規則見 §4.1。
- **抽不到的欄位一律 `null`,不編造、不猜測**(沿用廠商讀取器同一護欄)。
- 整份 PDF 抽不到任何文字 → `readAwardNotice` throw,訊息明說是掃描件。

### 5.3 業務層(懂 PMIS 與監造報表)

**`app/server/project-basics.js`** — 新檔

```js
compareBasics(award, project) -> Array<{ 欄位, 決標公告值, 主檔值, 一致 }>  // 純函式
basicsToOperations(values)    -> Array<setCell>                          // 純函式,給 SP0
```

`basicsToOperations` 產出 `工程基本資料!B1..B8, B10` 的 `setCell`(B9 是範本公式,不寫)。
B8 開工日期寫 **Excel 日期序號**(範本 B8 原本就是序號,且 B9 公式 `=B8+B7-1` 做日期算術),
不寫 ISO 字串。序號基準:Excel 1900 日期系統,`1899-12-30` 為第 0 天。

**`app/server/report-workbook.js`** — 新檔

```js
workbookPath(projectId)   -> string          // data/reports/project_<id>/監造報表.xlsm
ensureWorkbook(projectId) -> Promise<string> // 不存在則從版控範本複製,回絕對路徑
```

專案的監造報表 `.xlsm` 是**常駐檔**:SP1 建立並寫基本資料,SP2 往同一份寫契約詳細價目表,
SP3 往同一份寫每日施工紀錄。路徑根沿用既有 `PMIS_DATA_DIR` 慣例(見 `parsers/registry.js`),
不寫死絕對路徑。

**`app/server/project-basics-routes.js`** — 新檔

| 端點 | 行為 |
|---|---|
| `POST /api/projects/:id/award-notice`(multipart PDF) | `readAwardNotice` → `compareBasics` → 回 `{ parsed, project, diffs }`。不落庫、不寫檔。 |
| `POST /api/projects/:id/basics`(9 值 JSON) | 硬擋檢查 → `ensureWorkbook` → `fillTemplate` → 讀回 B9 → 回寫 `projects` → 回 `{ ok, workbookPath }` |

回寫 `projects` 的欄位:`project_no`(工程編號)、`name`(工程名稱)、`award_amount`(契約金額)、
`start_date`(開工日期)、`contract_completion_date`(讀回的 B9)、`supervisor_firm`、`designer_firm`。
`vendor_id` / `school_id` 是外鍵,承包廠商與主辦機關若與主檔不符,由承辦人在畫面上裁決後
**只更新報表值、不自動改綁外鍵**(改綁廠商/學校屬既有廠商與學校管理功能,不在本 SP 範圍)。

### 5.4 前端

`app/public` 內新增「工程基本資料」頁:上傳決標公告 → 表格呈現「決標公告值 / 主檔值 / 裁決」
三欄 → 逐欄裁決 → 填開工日期 → 送出。配色一律走 `app.css` 的 CSS 變數(遵 CLAUDE.md §2),
錯誤框套 `.error-msg`。

## 6. 資料流

```
上傳決標公告 PDF
  → extractRows → parseAwardNotice → 5 值
  → compareBasics(5 值, projects 主檔) → 差異清單
  → 畫面逐欄裁決(採公告 / 採主檔 / 手動輸入)
     ＋ 人工輸入 B7 契約工期、B8 開工日期(對照開工報告表 PDF)
     ＋ B2/B4 由 settings 帶入,可改
  → 送出:仍有未裁決差異 → 400 硬擋
  → ensureWorkbook → fillTemplate 寫 B1:B8,B10
  → 讀回 B9(範本算出的完工期限)→ 回寫 projects
```

## 7. Schema 異動

```sql
ALTER TABLE projects ADD COLUMN supervisor_firm TEXT;  -- 監造單位,空則吊 settings
ALTER TABLE projects ADD COLUMN designer_firm   TEXT;  -- 設計單位,空則吊 settings
```

`settings` 為既有 key/value 表,新增兩個 key:`supervisor_firm`、`designer_firm`。

**契約工期不另存欄位**,由 `contract_completion_date − start_date + 1` 推得;
`projects` 既有的 `project_no` / `name` / `vendor_id` / `school_id` / `start_date` /
`contract_completion_date` / `award_amount` 即為主檔側的 7 個對照值。

`db.js` 的 `migrate()` 目前只有 `CREATE TABLE IF NOT EXISTS`、沒有欄位級 migration 機制;
本 SP 需在 `migrate()` 內加一段冪等的 `ADD COLUMN IF NOT EXISTS`,並確認 pg-mem 可跑
(既有測試全走 pg-mem)。

## 8. 範本落點

公版範本目前只在 `docs/samples/監造報表範本/監造報表_空白公版範本.xlsm`,那是**範例庫**語意,
程式不應相依 `docs/`。搬一份到 `app/templates/監造報表_空白公版範本.xlsm` 當正式底稿。
該路徑不受任何 `.gitignore` 規則影響(已用 `git check-ignore` 確認),可直接版控。
`docs/samples/監造報表範本/` 那份保留作對照範例,不刪。

## 9. 錯誤處理

| 情境 | 行為 |
|---|---|
| 上傳的 PDF 抽不到任何文字(掃描件) | 明確報「此決標公告為掃描件,無法解析」。**不做 OCR fallback、不猜測** |
| 單一錨點抓不到 | 該欄回 `null`,畫面標「未能解析,請手動輸入」,不阻擋其餘欄位 |
| 仍有未裁決差異就送出 | 400 硬擋,列出所有未裁決欄位(與 SP3「硬錯阻擋 + 列全部錯誤」一致) |
| Excel COM 三次重試仍失敗 | 整個動作失敗,**不回寫 `projects` 主檔**,避免主檔與報表不一致 |

## 10. 測試(Rule 9:測「為什麼」,不是測「做了什麼」)

單元測(純函式,不需 Excel):

| 測什麼 | 為何而測 | fixture |
|---|---|---|
| 得標廠商取 `是否得標=是` | 取第一家的爛實作必須被打掛 | 仁德(第 2 家)、四湖永慶(第 3 家) |
| x 三分欄:區塊直排字不得混進標籤 | 混進去會讓「機關名稱」變「機機關名稱」而抓不到 | 人造含 x<45 直排字的 items |
| y ±3 容差合併 | 同列標籤與值的 y 會差 1~3px,不容差就配不到 | 人造 y 差 2 的 items |
| 抽不到 → `null` | 編造值會污染契約基準,後續 SP2/SP3 全錯 | 人造缺欄 rows |
| `compareBasics` 三態 | 一致 / 不一致 / 缺值須分得開,否則硬擋會誤判 | 人造組合 |
| 開工日期 → Excel 序號 | 寫錯基準日整份報表日期全偏 | `2026-06-19` → `46192`(對照宜梧實例) |

整合測(需 Excel COM,比照 SP0 的 `template-engine.integration.test.js`):

- 寫入 B1:B8,B10 後讀回,斷言值落地、**B9 公式仍在**且算出 `B8+B7-1`、巨集仍存在。

fixture 政策:決標公告 PDF 為大二進位,依 `docs/samples/.gitignore` 不版控;
需要當測試 fixture 時,挑代表性小檔複製進 `app/tests/fixtures/`(沿用既有慣例)。
若 PDF 本身仍過大,改以 `extractRows` 的輸出(JSON)當 fixture,純函式測試本來就吃 rows。

## 11. 不在範圍

- 不做 OCR、不解析開工報告表掃描件。
- 不動既有 `extractPages()` 與廠商讀取器 registry。
- 不做 SP-P 的 docType 一般化(SP1 已不需要)。
- 不碰契約詳細價目表(SP2)、每日施工紀錄(SP3)、公文(SP4)。
